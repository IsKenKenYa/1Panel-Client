# HAR/HSP 依赖和构建验证

## 先确认依赖能不能改

检查顶层和模块级 `build-profile.json5`、`oh-package.json5`、lockfile、import、本地 `.har`/`.hsp` 文件和模块源码路径。把受影响的依赖分成三类：

1. **源码在当前工程内。** 确认模块类型和所有调用方。如果超出用户授权范围，先询问是否纳入；获得同意后，与应用一起迁移和构建。
2. **只有归档包或下载包。** 不要编辑 `oh_modules`/`node_modules` 中包管理器维护的文件，也不要原地改二进制归档。检查公开声明和导出（`index.ets`、`Index.ets`、`.d.ets`、`.d.ts`、包元数据及供应方文档）是否有 V2 组件或 model。
3. **源码在别处且当前不可用。** 在用户提供或授权源码前，按外部依赖处理。

依赖名或目录名带有 “V2” 不能证明它真的可用，必须检查实际导出。先核实导出，再决定是否保留桥接：完整场景迁移且有适用的 V2 导出时，确认最低 API/工具链要求后切换 import、组件调用和输入/事件契约；不能只把页面改成 V2、保留可迁移的 V1 组件。“归档不可修改”不等于“归档只导出 V1”，“尚未查到”也不等于“没有 V2”。只有确认仅有 V1，或范围/版本不允许替换时，才按 [interop.md](interop.md) 保留边界并说明依据。只核对当前任务实际使用的导出，不扫描整个 SDK。

源码形式的 HSP/HAR 还要检查公共 re-export。内部组件已迁移，但模块公共 index 仍导出旧符号时，不能算完成。

## 找到工程实际的构建方式

不要写死某台机器的路径。先找到工程根目录，再使用仓库自己的 wrapper、文档、脚本或已配置的 DevEco/Hvigor 工具链。可能的入口包括纳入版本控制的 `hvigorw`/`hvigorw.bat`、仓库脚本或可用的 `hvigor` 命令，但只能使用工程实际提供的方式。

记录：

- 命令和工作目录；
- product/build mode 和模块 target；
- 工具链/SDK 版本；
- 生成的是 HAP、APP、HSP、HAR，还是多个产物。

构建所有已修改的交付物。整应用迁移通常需要应用 HAP/APP target 以及修改过的库/HSP/HAR；组件级迁移至少要构建会编译该组件及其调用方的应用 target。

## 构建验证循环

1. 条件允许时，编辑前先执行基线构建。
2. 迁移后从工程根目录执行相同构建。
3. 将第一批有效错误分为：迁移回归、基线已有错误、SDK/API 不支持，或外部依赖不可用。
4. 在授权范围内修复迁移导致的错误并重新构建。多处出现同类错误时，先搜索共同模式再批量修复。
5. 如果工程有测试或 UI 测试，执行与双向数据流、嵌套观察、storage 持久化和列表复用相关的测试。

应用构建被要求但跳过或失败时，不能说“迁移已验证”。报告确切阻塞项、最后执行的命令和输出摘要。没有工程元数据的独立代码片段不做虚构的构建，只能进行源码级检查。

## 构建后优先检查这些行为

- 嵌套属性变化和整对象替换是否刷新 UI；
- 父到子更新和子到父事件是否仍然生效；
- `@Monitor` 副作用的时序；
- 真实组件层级中的 Provider/Consumer alias；
- 跨页面和 Ability 的 AppStorage/LocalStorage key；
- 已安装旧版本上的持久化数据升级；
- Repeat item 身份、滚动、缓存/复用生命周期和 template 变体；
- 高级组件事件和公共 model 类型；
- debug/release 编译标志不同时的结果。
