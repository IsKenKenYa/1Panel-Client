# ArkUIDumpViewer 用户使用指南

当前工具处于迭代中，未正式release，功能更新较频繁，可关注2.1章节更新信息

## 1. 概述

ArkUIDumpViewer 是一款 ArkUI 组件树内存分析工具。它将 ArkUI 性能动态测试产生的 dump 文件解析为可视化的组件树、布局视图、动态统计图表和版本对比报告，帮助定位内存占用热点、不可见组件泄漏和版本间内存回归。

核心功能：

- **树视图**：以交互式节点图展示组件树结构，支持搜索、折叠、节点详情查看
- **布局视图**：以线框矩形展示组件在屏幕上的布局边界
- **动态统计视图**：按步骤展示内存变化折线图 + 分类表 + 步骤差异面板
- **版本对比视图**：跨版本内存对比折线图 + 峰值对比

## 2. 安装与运行

### 2.1 安装

发布版为 npm 包 `arkui-dump-viewer-1.0.0.tar.gz`，支持全局安装或直接运行：

```bash
# 全局安装
npm install -g arkui-dump-viewer-1.0.0.tar.gz

# 或不安装直接运行
npx arkui-dump-viewer-1.0.0.tar.gz <input> [options]
```

### 2.2 命令语法

```
arkui-dump-viewer <input> [options]
```

| 参数 | 缩写 | 说明 | 默认值 |
|------|------|------|--------|
| `<input>` | — | dump 文件路径或包含 dump 文件的目录（必填） | — |
| `--csv <path>` | `-c` | 自定义组件内存参考表（memory.csv）路径 | 使用内置参考表 |
| `--output <dir>` | `-o` | 输出目录 | `./dumps_result_YYYY-MM-DD` |
| `--version-config <path>` | `-v` | 版本配置文件（version-config.json）路径 | 自动搜索输入目录附近或使用内置配置 |
| `--incremental` | — | 增量构建：跳过未变化的 dump，仅重新解析变化的应用（**默认行为**） | 默认开启 |
| `--force` | — | 强制全量构建，忽略缓存 | — |
| `--help` | `-h` | 显示帮助信息 | — |

### 2.3 输入模式

根据 `<input>` 参数自动判断：

- **单文件模式**：传入 `.dump` 文件路径，工具自动创建临时目录处理，应用名取文件名
- **目录模式**：传入目录路径，自动扫描其中的 dump 文件（支持第 4 章所述的三种目录结构和版本层布局）

### 2.4 输出产物

工具在输出目录下生成：

| 文件 | 说明 |
|------|------|
| `index.html` | 自包含交互式 HTML 查看器（支持 `file://` 协议，无需 Web 服务器） |
| `dataset_<ver>_<app>.js` | 各应用 dump 数据的 JS 文件（稳定命名，按需加载） |
| `usecase_<ver>_<app>.js` | 各应用用例步骤数据（动态统计视图使用） |
| `version_compare.js` | 版本对比数据（仅版本层布局时生成） |
| `ArkUI内存分析汇总_*.xlsx` | 内存分析汇总表（非版本布局一个文件；版本布局每个版本一个文件，包含该版本所有应用） |
| `ArkUI动态统计_*.xlsx` | 动态统计表（每个应用一个 sheet） |
| `images/` | SVG 图表（仅版本层布局） |
| `build-manifest.json` | 增量构建缓存清单（记录各应用 dump 的 mtime 和累加器数据，供增量构建复用） |

### 2.5 增量构建

工具默认使用增量构建模式：首次运行时执行全量构建，后续运行仅重新解析发生变化的 dump 文件，从缓存的累加器数据重建聚合输出。

**工作原理**：
- 首次构建生成 `build-manifest.json`，记录每个应用的 dump 文件修改时间和解析结果摘要
- 后续构建对比 dump 文件的 `mtime`，跳过未变化的文件，仅重新解析变化的应用
- XLSX、index.html 等聚合产物始终从累积数据重建，确保数据一致性
- SVG 图表仅对变化的应用重新生成

**缓存目录**：增量构建使用 `dumps_result_latest` 符号链接指向的目录（或 `--output` 指定的目录）作为缓存位置。

**强制全量**：使用 `--force` 可忽略缓存，强制重新解析所有 dump 文件。

**定向更新**：使用 `--target <版本/应用>` 可指定只更新某个版本或应用的 dump 数据，其他应用直接复用缓存：

| 用法 | 说明 |
|------|------|
| `--target B032/抖音` | 仅重新解析 B032 版本的抖音应用 |
| `--target B033` | 重新解析 B033 版本下的所有应用 |
| `--target 无版本/wexin` | 重新解析"无版本"分组下的 wexin |

**仅生成汇总表**：使用 `--xlsx <版本>` 可从缓存的 `build-manifest.json` 数据直接生成指定版本的 XLSX，无需重新解析 dump 文件：

| 用法 | 说明 |
|------|------|
| `--xlsx B035` | 从缓存生成 B035 版本的内存分析汇总和动态统计 XLSX |

前提：需要先执行过一次全量或增量构建，确保 `build-manifest.json` 中有目标版本的数据。

定向更新时，目标应用会被重新解析（无论 mtime 是否变化），其他应用从 `build-manifest.json` 复用缓存数据。所有输出产物（XLSX、SVG、index.html、version_compare.js）都会重新生成，确保目标应用的更新数据生效到树视图、布局视图、动态统计和版本对比中。

### 2.6 使用示例

```bash
# 首次运行：全量构建（自动）
arkui-dump-viewer ./dumps

# 后续运行：增量构建（自动，仅重新解析变化的 dump）
arkui-dump-viewer ./dumps

# 强制全量重建
arkui-dump-viewer ./dumps --force

# 定向更新：仅重新解析 B032 版本的抖音
arkui-dump-viewer ./dumps --target B032/抖音

# 定向更新：重新解析 B033 版本所有应用
arkui-dump-viewer ./dumps --target B033

# 指定自定义内存参考表和输出目录
arkui-dump-viewer ./dumps -c custom-memory.csv -o ./my-results

# 指定版本配置文件
arkui-dump-viewer ./dumps --version-config ./version-config.json

# 处理单个 dump 文件
arkui-dump-viewer photo.dump

# 使用缩写
arkui-dump-viewer ./dumps -c my.csv -v ./version-config.json -o ./out
```

**npm run build 用法**：通过 npm 运行时，脚本参数需加 `--` 分隔：

```bash
# 全量构建（默认）
npm run build

# 增量构建
npm run build:incremental

# 定向更新
npm run build:target B032/抖音

# 仅生成指定版本的汇总表
npm run build:xlsx B035
```

> **注意**：`npm run build` 默认执行全量构建。增量构建使用 `npm run build:incremental`，跳过未变化的 dump 文件。

### 2.7 注意事项

- 工具自动以 `--max-old-space-size=8192` 运行，避免大 dump 集的内存溢出
- 内置 `memory.csv` 包含常见组件的内存参考值；如需自定义，通过 `--csv` 指定
- 内置 `version-config.json` 包含默认版本目录匹配规则；如需自定义，放在 `dumps/` 同级目录或通过 `--version-config` 指定
- 打开输出的 `index.html` 即可使用第 5 章所述的所有交互功能
- 增量构建时，删除某个应用的 dump 目录后再次构建，该应用的输出文件会被自动清理

## 3. 准备测试数据

### 3.1 Dump 文件来源

ArkUIDumpViewer 解析的是 ArkUI 性能动态测试工具产生的 `*.dump` 文件。每个 dump 文件包含某一时刻应用界面的完整组件树快照。

### 3.2 目录结构

将 dump 文件放置在 `dumps/` 目录下，工具会自动识别三种应用级目录结构和一种版本层布局。

#### 场景 1：编号用例子目录

每个用例一个子目录，dump 文件按名称区分为"步骤"和"回桌"：

```
dumps/
  B站/
    01/
      PerformanceDynamic_bilibili_0010_case_step_1.dump  ← 前台步骤
      PerformanceDynamic_bilibili_0010_case_step_2.dump
      PerformanceDynamic_bilibili_0010_backhome.dump     ← 回桌面
    02/
      PerformanceDynamic_bilibili_0020_case_step_1.dump
      PerformanceDynamic_bilibili_0020_backhome.dump
  美团/
    case_0010/
      0/arkuidump/
        PerformanceDynamic_meituan_0010_case_step_1.dump
        PerformanceDynamic_meituan_0010_backhome.dump
```

**命名规则**：
- `*_step_N.dump` → 前台步骤（第 N 步）
- `*_backhome.dump` → 回桌面/后台
- `*_gohome.dump` → 回应用首页

**目录名识别**：纯数字（`01`、`02`）、`case_NNNN`、`PerformanceDynamic_xxx_NNNN` 均被识别为用例目录。如果用例目录下没有直接的 dump 文件，会自动递归搜索子目录（适配 `case_NNNN/0/arkuidump/` 等嵌套布局）。

#### 场景 2：扁平文件 + 关键词/内存峰值识别

dump 文件直接放在应用目录下。工具通过文件名关键词和实际内存对比来识别前台峰值和后台均值：

```
dumps/
  京东/
    首页-峰值.dump        ← "峰值" → 前台峰值
    首页-后台.dump        ← "后台" → 后台均值
  微博/
    微博前台峰值.dump
    微博后台均值.dump
  weixin/
    PerformanceDynamic_weixin_0110_case_step_1.dump   ← 无关键词，自动对比内存
    PerformanceDynamic_weixin_0110_case_step_2.dump
    ...
    PerformanceDynamic_weixin_0110_backhome.dump       ← "backhome" → 后台均值
```

**识别规则**：
1. 含后台关键词的文件（`后台`、`均值`、`background`、`avg`、`average`、`bg`、`backhome`、`back`）→ 后台均值 Dataset
2. 其余文件按**实际内存（NativeHeap + DMA）对比**，取内存最高的步骤作为前台峰值 Dataset
3. 所有步骤均参与动态统计和版本对比，不论是否为峰值

> **注意**：旧版本依赖文件名中的前台关键词（`前台`、`峰值`等）识别峰值。当前版本改为实际内存对比，即使文件名无任何关键词也能正确识别峰值步骤。

#### 场景 3：顺序步骤（无关键词）

同一应用目录下多个 dump 文件，文件名不含前后台关键词，视为一个用例的连续步骤，按文件修改时间排序。工具自动对比各步骤内存，取内存最高者作为前台峰值：

```
dumps/
  抖音/
    S1、启动抖音(等待5s).dump    ← 步骤 1
    S2、进入热点页面.dump        ← 步骤 2
    S3、页面浏览.dump            ← 步骤 3
```

**识别规则**：所有文件均为步骤，按实际内存对比取峰值步骤生成前台峰值 Dataset，其余步骤仅参与动态统计。

#### 降级回退

如果 dump 文件名不匹配 `*_step_N` / `*_backhome` / `*_gohome` 等模式（场景 1），也不含前后台关键词（场景 2），工具会自动将目录下所有 dump 文件按**文件修改时间**排序，作为顺序步骤处理（场景 3），并按实际内存对比识别峰值。

#### 版本层布局

在应用层之上增加版本目录，用于跨版本对比：

```
dumps/
  B033/
    B站/
      01/
        PerformanceDynamic_bilibili_0010_case_step_1.dump
    美团/
      case_0010/
        ...
  B035/
    B站/
      01/
        PerformanceDynamic_bilibili_0010_case_step_1.dump
    美团/
      case_0010/
        ...
  番茄畅听/          ← 非版本目录，归入"无版本"分组
    case0/
      ...
```

**检测方式**（优先级从高到低）：

1. **版本配置文件**（推荐）：在 `dumps/` 同级或内部放置 `version-config.json`，工具根据配置中的 `dirPattern` 匹配顶层目录名，匹配上的为版本目录，未匹配的视为应用目录。详见 §3.4。

2. **自动检测**（无配置文件时的回退）：当 `dumps/` 下存在 ≥2 个顶层目录，且这些目录共享 ≥2 个相同子目录名时，自动识别为版本层布局。

**无版本归组**：当目录结构不是版本层布局时，所有应用自动归入"无版本"分组；当使用版本配置文件时，不匹配任何版本模式的目录也会归入"无版本"分组。

### 3.4 版本配置文件（version-config.json）

当 `dumps/` 下的版本目录名与测试版本名称不完全一致时（例如目录名为 `B033` 而测试版本全称为 `6G JAL-AL90 207.0.0.33(C00E35R4P2)版本`），可通过配置文件显式指定版本目录的匹配规则和显示名称。

**配置文件搜索位置**（按优先级从高到低）：

1. `--version-config` / `-v` 命令行参数指定的路径
2. 环境变量 `VERSION_CONFIG` 指定的路径
3. `dumps/` 同级目录下的 `version-config.json`
4. `dumps/` 目录内的 `version-config.json`
5. 工具内置的 `version-config.json`（随 npm 包发布）

**推荐做法**：将 `version-config.json` 放在 `dumps/` 同级目录下，工具会自动识别。如果配置文件位于其他位置，使用 `--version-config` 指定：

```bash
arkui-dump-viewer ./dumps --version-config /path/to/version-config.json
```

**文件格式**：

```json
{
  "_comment": "测试版本与应用版本对应关系配置",
  "versions": [
    {
      "dirPattern": "B033",
      "displayName": "B033 (7.0.0.33)",
      "apps": {
        "今日头条": "17.6.0",
        "微博": "16.6.1",
        "拼多多": "8.16.0"
      }
    },
    {
      "dirPattern": "B035",
      "displayName": "B035 (7.0.0.35)",
      "apps": {
        "微信": "8.0.19.45",
        "抖音": "39.8.0"
      }
    },
    {
      "dirPattern": "NewVersion",
      "displayName": "新版本",
      "apps": {}
    }
  ]
}
```

> **提示**：`apps` 字段为可选。不填应用版本号时，折线图标签仅显示版本名（如 `B033`）；填写后显示为 `B033 (8.0.19.37)` 格式。只需定义 `dirPattern` + `displayName` 即可让工具识别版本目录。

**字段说明**：

| 字段 | 必填 | 说明 |
|------|------|------|
| `dirPattern` | 是 | 目录名匹配模式，支持 `*`（任意字符）和 `?`（单个字符）通配符，不区分大小写 |
| `displayName` | 是 | 版本在 UI 中的显示名称（如版本选择器、XLSX 文件名、折线图标签）。无需包含应用版本号，仅标识测试版本即可 |
| `apps` | 否 | 该测试版本下各应用的应用版本号。填写后版本对比折线图标签会显示为 `B033 (8.0.19.37)` 格式 |

### 3.3 operationRecord.txt（可选）

在用例目录下放置 `operationRecord.txt` 可为步骤提供操作描述。工具会在用例目录及其子目录中搜索此文件。

**文件格式**：
```
time:xxx,case_name:xxx,package_name:xxx,operation:1、启动应用
time:xxx,case_name:xxx,package_name:xxx,operation:2、进入首页
time:xxx,case_name:xxx,package_name:xxx,operation:3、页面浏览
```

工具解析每行的 `operation:` 字段，提取行首的数字编号（如 `1、`、`15、`）作为步骤号。

## 4. 功能页面

### 4.1 树视图

树视图以交互式节点图展示组件树结构。每个节点为一个圆形，颜色标识状态：

| 颜色 | 状态 | 含义 |
|------|------|------|
| 绿色 | 在树显示 | 节点在组件树上且可见 |
| 橙色 | 在树隐藏 | 节点在组件树上但不可见（被 NavDestination/TabContent/Swiper 隐藏，或 VisibleAndActive=0） |
| 灰色 | 游离 | 节点已脱离主树（detached） |

**节点显示**：
- 圆内显示组件标签（截断至 10 字符）
- 圆下方显示子树内存（热力色：绿色=低、红色=高）
- 折叠节点显示 `+N` 标识（隐藏子节点数量）
- 聚合节点（如 `Image x42`）以斜体+虚线边框标识

**交互**：

| 操作 | 效果 |
|------|------|
| 悬停节点 | 浮动信息卡片：标签、ID、内存、状态、子节点数、子树内存；Image/XComponent/Web 额外显示 DMA、组件尺寸 |
| 单击节点 | 固定信息卡片（再点取消）；选中节点显示右侧详情面板 |
| 单击聚合节点 | 左侧展开该类组件明细表（ID、compid、状态、尺寸、内存、DMA；Image 额外显示类型/原始尺寸/优化建议） |
| 双击节点 | 折叠/展开子树 |
| 滚轮 | 缩放（4%~400%，朝光标位置缩放） |
| 拖拽画布 | 平移视图 |
| 点击空白处 | 取消选中，隐藏固定信息卡片 |

**工具栏按钮**：

| 按钮 | 功能 |
|------|------|
| 展开 | 展开所有节点并适应屏幕 |
| 隐藏态 | 折叠纯可见分支，仅保留含隐藏节点的路径 |
| 折叠 | 折叠所有有子节点的节点 |
| 适应 | 缩放至全部可见内容 |
| + / - | 放大/缩小 5% |

**搜索**：搜索框支持按标签、ID、AccessibilityId、ComponentName、compid、Content、Description、状态过滤。匹配节点加橙色边框，不匹配节点半透明（25%），匹配祖先自动展开，显示匹配数量。

**数据集选择**：工具栏下方提供版本→应用→用例的级联选择器。选择版本后刷新应用列表，选择应用后刷新用例列表。每个用例为一个下拉菜单，可选择查看任意步骤的组件树，前台峰值步骤标记为【前台峰值】，后台均值步骤标记为【后台均值】。

**左侧图表面板**：
- 节点状态统计：各状态数量 + NativeHeap 内存
- 组件内存参考表：各类组件的数量、单实例内存、总内存（按总内存降序）
- 面板可折叠、可拖拽

**右侧独立树面板**：
- 主树 vs 游离树的 NativeHeap/DMA/总内存分布
- CAPI 组件统计：在树 vs 游离（命令式 CAPI Node / FrameNode / RenderNode / BuilderNode）
- 游离类型分布
- 独立树列表：点击切换渲染对应树
- 面板可折叠

### 4.2 布局视图

布局视图以线框矩形展示组件在屏幕上的布局边界。

- 有 frame（w>0, h>0）的节点绘制为矩形，颜色与树视图相同（绿/橙/灰）
- 矩形按面积从大到小绘制（大矩形在底层）
- 显示设备边框作为背景
- 尺寸足够的矩形（w>54, h>18）显示 Content 或标签文字
- 搜索时非匹配节点近乎透明（2%）

**交互**：与树视图相同的悬停、点击、搜索、缩放、平移行为。

## 6. 节点状态与内存计算

### 6.1 三种状态

| 状态 | 条件 | 颜色 |
|------|------|------|
| 在树显示 | 节点在主树上且可见 | 绿色 |
| 在树隐藏 | 节点在主树上但被隐藏（父节点隐藏，或 VisibleAndActive=0） | 橙色 |
| 游离 | 节点已脱离主树（detached=true） | 灰色 |

### 6.2 内存口径

- **NativeHeap（基础内存）**：每个组件的标签对应一个基础内存值（来自内存参考表），无匹配时默认 4kb
- **DMA 内存**：
  - Image（非 pixmapID、非 SVG）：宽 × 高 × 4 / 1024 kb
  - XComponent / Web：宽 × 高 × 4 × 5 / 1024 kb（含多缓冲）
  - pixmapID / SVG：不计 DMA（共享像素内存或矢量资源）
- **总内存** = NativeHeap + DMA

### 6.3 不可见内存分类

| 分类 | 含义 |
|------|------|
| 不可见 Navigation 页面 | 被 NavDestination 隐藏的页面 |
| 不可见 Tab 页 | 非当前 TabContent 页面 |
| 不可见 Swiper 页 | 非当前 Swiper 页面 |
| 不可见缓存池 | LazyForEach / Repeat / Reusable 缓存 |

不可见组件进一步细分为：属于不可见页面 / 在树隐藏（散装）/ 不可见列表缓存。

## 7. 常见问题

**Q：dump 文件必须按特定命名吗？**
A：场景 1 需要 `*_step_N.dump` 和 `*_backhome.dump` 命名规则。场景 2 依赖文件名中的关键词。场景 3 不限制命名。版本层布局只影响顶层目录名，内部仍使用场景 1/2/3 规则。

**Q：版本对比视图为什么看不到？**
A：版本对比视图仅在使用版本层布局（`dumps/{version}/{app}/...`，≥2 个版本）时出现。非版本层布局时，版本选择器中显示"无版本"分组，但版本对比视图不显示。如果 `dumps/` 下有版本目录但未被识别，请添加 `version-config.json` 配置文件（见 §3.4），或通过 `--version-config` 指定配置路径。

**Q：动态统计视图没有数据？**
A：动态统计视图需要场景 1（编号用例子目录）或场景 2/3（扁平/顺序文件）的数据。工具会自动对比各步骤内存识别峰值，所有步骤均参与动态统计。

**Q：步骤标签显示为数字而非操作描述？**
A：在用例目录下放置 `operationRecord.txt` 文件，工具会自动解析操作描述作为步骤标签。

**Q：聚合节点（如 `Image x42`）如何查看明细？**
A：单击聚合节点，左侧会展开该类组件的明细表，列出每个实例的 ID、compid、状态、尺寸、内存、DMA 等信息。Image 类型额外显示 URL 类型（pixmapID/SVG）、原始尺寸和优化建议。

**Q：增量构建和全量构建有什么区别？**
A：增量构建（默认）跳过未变化的 dump 文件，仅重新解析发生变化的 app，从缓存重建聚合输出。首次运行为全量构建，后续自动增量。使用 `--force` 可强制全量重建。增量构建通过 `build-manifest.json` 中的 mtime 对比判断文件是否变化。
