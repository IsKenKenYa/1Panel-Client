# HAP 劣化案例模式（.abc / .so）

> 本文档定义 HAP 维度劣化的典型案例模式，供综合报告第八章「劣化点汇总与优化建议」根因匹配使用（案例库范围与匹配规则见 `SKILL.md` 第八章）。
>
> 匹配到下列案例时：可引用案例的根因推断与修复方向，并标注出处（如「见 hap.md 一、.abc 劣化」）。未匹配到时：8.1 根因列写「未匹配案例库，需人工核查」，不给修改建议。
>
> **so_size 判定口径（统一）**：某 SO 在 A 版本无映射（smaps 无该项 / `is_new=true`）时，A 侧 so_size 与 Pss 均记为 0；B 侧只要出现映射（so_size > 0 或 Pss > 0）即视为增长，无需 A 侧存在该 SO。

## 一、.abc 劣化

### 案例模式描述

arkts 应用中新增业务代码。新增的 ArkTS/TS 源码编译为 `.abc`（ArkTS 字节码）打包进 hap 包，hap 体积随之增大，加载后 `.hap` 映射的内存（Pss）增长。这类劣化与运行时堆分配无关，本质是**编译产物体积增长**。

### 匹配规则

> **输入**：A/B 两版本目录下 `analysis/analysis_详细数据.xlsx`（或 `汇总.xlsx`）中 so 列为 `.hap`（或 `.HAP`）的行——即「一层领域/二层领域 → .hap → HAP」明细，size / type_size 列即该版本 hap 加载占用。取两版本同名行做差。

1. **`.hap` size 增长**：B 版本 `analysis_详细数据.xlsx` 中 so 为 `.hap` 行的 size（type_size），大于 A 版本对应值（`delta > 0`），对应劣化类型为「二进制膨胀」。

命中该规则后，根因方向即指向 hap 包内产物增长；其中 ArkTS 新增业务代码编译为 `.abc` 是最常见来源。

## 二、.so 劣化（二进制体积增长）

### 案例模式描述

自定义 so 中新增业务代码。native 侧自定义 so（应用自研 so，非系统库）新增 C/C++ 业务代码，编译后 so 二进制体积增大，加载后该 so 的映射内存增长。这类劣化与运行时堆分配无关，本质是**二进制体积增长**。

### 匹配规则

> **输入**：对比报告第四章「Top10 劣化 SO」章节内容（表格列：# / SO / 归属领域 / type_name 明细 / 旧版(MB) / 新版(MB) / 差值(MB)；排名规则为以 SO 为键累加各 type_name 差值、按总差值降序取前 10、排除虚拟分类）。逐行按下列规则判定。

1. **Top10 表中该 SO 差值为正**：该 SO 行出现在第四章 Top10 劣化 SO 表中，「差值(MB)」列 > 0，且该 so 为应用自定义 so（按「归属领域」列判断归属，排除系统库；归属推断见 `so-size-hap-workflow.md` 步骤 4）。
2. **type_name 明细含 SO_SIZE 增长**：该行「type_name 明细」列含 `SO_SIZE: +X.XX` 项（挂载在该 so 下的 SO_SIZE 明细差值为正，对应劣化类型「二进制体积增大」）；「旧版(MB)」/「新版(MB)」列即 A/B 侧 so_size（A 版无映射时旧版记 0，见头部判定口径）。
3. **归属领域为「三方自研代码」**：该 SO 行「归属领域」列的一层领域为「三方自研代码」（如「三方自研代码/其他三方库」「三方自研代码/三方运行时」）；「归属领域」为空或其他一层领域（系统SDK、语言运行时、WEB、三方ArkTS库 等）的 SO 不属于本案例模式，按未匹配处理。

三条规则全部通过即确认：劣化源于 so 二进制体积增大（新增代码段/数据段）。type_name 明细中 SO_SIZE 无正差值的情形（如仅 NATIVE_HEAP 等运行时类型增长、Pss 增长但 SO_SIZE 不变）不属于本案例模式。
