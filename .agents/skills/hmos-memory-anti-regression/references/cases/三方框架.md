# 三方框架 劣化案例模式（KMP / RN / Flutter）

> 本文档定义三方框架（KMP、RN、Flutter）维度劣化的典型案例模式，供劣化点根因匹配使用。匹配到下列案例时：可引用案例的根因推断并标注出处（如「见 三方框架.md · RN 一、新增 RN 的使用」）；未匹配到时：根因列写「未匹配案例库，需人工核查」，不给修改建议。

## KMP

### 新增 KMP 的使用

#### 案例模式描述

应用从无到有引入并使用 KMP（Kotlin Multiplatform）。KMP 运行时与桥接层随首次初始化加载，其 native 模块与 so 映射从无到有，so 总占用增长。这类劣化本质是**目标业务路径新增 KMP 初始化**，属框架引入型增长，需评估引入必要性。

#### 匹配规则

1. **KMP 运行时 so 从无到有（数据规则）**：A/B 两版 so maps 对比中，劣化侧新增 KMP 相关 so 映射（A 侧无、B 侧有），对应 so 总占用从 0 增长（含 SO_SIZE/NATIVE_HEAP/OTHER 等 type_name）。
2. **源码核查 KMP 初始化路径（核查规则）**：检查业务路径是否在进入后初始化 KMP 并保留。检查要点：
   - 是否在业务页面/路径中调用 KMP 初始化入口（KMP bridge / engine init）；
   - 初始化后的 KMP 上下文/对象是否常驻未释放（约 20 MiB 量级常驻）。

两条规则同时命中即确认：劣化源于目标业务路径新增 KMP。规则 2 未发现初始化代码时，仅凭规则 1 不得下此结论，根因列写「未匹配案例库，需人工核查」。

### KMP 内存使用增加

#### 案例模式描述

应用已有 KMP 路径，新版本在相同初始化路径下 KMP 占用内存增加（如初始化数据量变大、常驻对象增多）。这类劣化本质是**已有 KMP 路径内存增长**，需对比新旧版本的 KMP 堆栈与常驻对象（含 native heap 与 OTHER 类型运行时分配）。

#### 匹配规则

1. **KMP 相关 so 总占用增长（数据规则）**：A/B 两版 so maps 对比中，KMP 相关 so 的总占用（所有 type_name 差值之和）B 侧较 A 侧增长（delta > 0）。KMP 运行时可能含非 malloc 分配（mmap 匿名页等 OTHER 类型），故须检查 SO 总增长而非仅 NATIVE_HEAP。
2. **源码核查 KMP 路径内存变化（核查规则）**：对比 A/B 两版源码 diff，相同 KMP 初始化路径中是否扩大了常驻数据/对象。检查要点：
   - KMP 初始化传参/预加载数据量是否增大；
   - 初始化后保留的常驻对象集合是否增多。

两条规则同时命中即确认：劣化源于已有 KMP 路径内存增加。规则 2 未发现路径内存变化时，仅凭规则 1 不得下此结论，根因列写「未匹配案例库，需人工核查」。

### 字符库重复加载

#### 案例模式描述

应用使用 RN，并注册多个自定义字体（ttf）。多个 ttf 经 RN 字体注册路径加载，字体资源与解析产物常驻，native heap 占用增长。典型场景有两种，均属本案例覆盖范围：

- **重复加载**：多个 RN 实例各自重复加载相同的字体文件——每个实例独立走字体注册流程，相同 ttf 被重复解析、常驻，native heap 出现大量相同大小的字体内存块。
- **注册量过大**：单个 RN 实例注册过多不同字体文件——每个 ttf 整文件字节经 `readRawFile` 加载并永久存留于 `FontRegistry::m_fontFileContentByFontFamily`，native heap 占用随注册数量线性增长。

这类劣化本质是**字体注册量过大/重复加载**，差异仅在字体注册环节。

#### 匹配规则

1. **`librnoh_core.so` 占用增加（数据规则）**：A/B 两版 so maps/native heap 对比中，劣化侧 `librnoh_core.so` 占用增加（RNOH 核心库承载字体注册路径）。
2. **`rnoh::FontRegistry::registerFont` 调用栈内存增大（数据规则）**：native heap 调用栈分析中，`rnoh::FontRegistry::registerFont` 帧下挂内存 B 侧较 A 侧增长；或出现大量相同大小的内存块（多 RN 实例重复加载相同字体文件所致）。
3. **源码核查字体注册路径（核查规则，补充核查非结论性门控）**：确认 RN 侧存在字体注册调用路径。检查要点：
   - 是否调用 `createAndRegisterRNInstance` 并传入 `fontResourceByFontFamily`（含字体文件映射）；
   - 字体注册产物是否常驻未释放（如 `m_fontFileContentByFontFamily` 永久持有整文件字节缓冲区）。

规则 1/2 命中即确认：劣化源于字符库重复加载/注册量过大。规则 3 为补充核查（确认具体字体注册路径与常驻行为），有源码时核查并补充结论，无源码时不影响匹配判定。

## Flutter

### 新增 Flutter 的使用

#### 案例模式描述

应用从无到有引入并使用 Flutter。Flutter 引擎随首次加载拉起 Flutter VM、Vulkan 渲染后端与图形编译相关 so，并触发 GPU 显存与 DMA 分配。表现为：

- 新增 `libflutter.so` 等 so 库及 so 总占用增长（含 SO_SIZE/NATIVE_HEAP/OTHER 等 type_name，Flutter 引擎运行时内存以 OTHER 类型为主——Dart VM heap 走 mmap 不走 native malloc）；
- 因 Flutter 走 Vulkan 渲染后端，触发 GPU 显存（`libvulkan.so`）与 DMA（`libbuffer_handle.z.so`）大幅增长。

这类劣化本质是**目标业务路径新增 Flutter 引擎**，属框架引入型增长。

#### 匹配规则

1. **Flutter 引擎 so 从无到有（数据规则）**：A/B 两版 so maps 对比中，劣化侧新增 `libflutter.so` 等映射，对应 so 总占用从 0 增长（含 SO_SIZE/NATIVE_HEAP/OTHER 等 type_name）。
2. **GPU 显存与 DMA 增长（数据规则）**：GPU 维度（`libvulkan.so`）与 DMA 维度（`libbuffer_handle.z.so`）对比中劣化侧增长明显，对应 Flutter Vulkan 渲染后端触发的显存与 buffer 增长。
3. **源码核查 Flutter 引入路径（核查规则，补充核查非结论性门控）**：检查业务路径是否引入 Flutter 并初始化引擎、加载页面。检查要点：
   - 是否调用 Flutter 引擎初始化入口（通过 UIAbility / startAbility 拉起 Flutter feature HAP）；
   - Flutter 引擎与 surface 是否常驻未释放。

规则 1/2 同时命中即确认：劣化源于新增 Flutter 的使用。规则 3 为补充核查（确认具体引入路径与 surface 释放行为），有源码时核查并补充结论，无源码时不影响匹配判定。
