# 案例匹配报告流程（可复用）

> **可复用步骤**：本流程对劣化源逐一匹配案例库并产出**匹配报告**（只给匹配结果与证据，不产出优化方案/优化建议）。主调用点为**步骤 6 综合报告第八章**（8.1 劣化源汇总的根因列）；也可在单个深度分析工作流（`native-heap-workflow.md` / `arkts-heap-workflow.md` / `so-size-hap-workflow.md`）产出劣化报告后单独调用，传入劣化报告与劣化类型判定即可。
>
> **遵循约束**：本流程遵循 `SKILL.md` 第八章「根因/建议限制」——**仅在案例库中匹配到对应场景时写根因，否则标注「未匹配案例库，需人工核查」，不臆测、不给建议**。优化 SKILL（harmonyos-memory-optimization-solution）的调用与主动优化执行不在本流程内，统一见 `references/optimization-skill-invocation.md`（SKILL.md 步骤 7）。

## 数据范围硬约束（最高优先级，覆盖全流程）

本流程所有判定证据**只能**来自以下两类路径内已存在的数据：

| # | 允许的数据来源 | 用途 |
|---|--------------|------|
| 1 | 调用方提供的**应用源码工程路径**下的源码 | 核查规则的源码核查（按案例「检查要点」逐项核对） |
| 2 | 调用方提供的**报告地址（输出目录）**下的所有采集数据与分析产物 | 数据规则判读（对比报告、`smaps_diff.json`、`analysis/*.xlsx`、`meminfo/` 采集文件、HAP 解包列表等**已落盘**产物） |

- **禁止通过任何操作现场获取新数据**：包括但不限于 `unzip` 解包 HAP、`hdc` shell/采集、`hiprofiler`/`hidumper`、重跑分析脚本生成新产物、网络获取。案例文档（如 `hap.md`）中出现的 `unzip -l` 等字样是对「报告地址下已存在解包产物」的引用，**不是**现场执行采集的授权。
- **证据缺失的处理**：规则所需数据不在上述两类路径内时，该规则按「无法判定」处理，所属案例按「未匹配」降级（见 1.2），并在输出中标注缺失的证据项供人工补采。**不得为补齐证据而执行任何采集操作。**

## 前置条件

| # | 条件 | 检查方式 | 不满足时 |
|---|------|---------|---------|
| 1 | 调用方已产出劣化分析报告 | 调用方 workflow 的「输出劣化报告」步骤已完成，含劣化类型 + 根因 + 源码位置 + 完整调用链 | 未完成则**终止**，本流程不负责劣化分析 |
| 2 | 调用方已判定劣化类型 | 调用方 workflow 的「归因根因」步骤已完成劣化类型判定（如泄露/延时释放/分配次数增加/单次分配变大/二进制膨胀等） | 未判定则**终止**，无劣化类型无法匹配案例 |
| 3 | 本地 `references/cases/` 目录存在 | 检查 `references/cases/` 目录可读，且至少含一个案例文档 | 目录缺失则子步骤 1 输出空列表，继续后续子步骤 |
| 4 | 分析步骤产物可读（按需） | 待匹配案例的规则涉及哪个分析步骤，该步骤产物即须可读（见 1.1 证据来源表） | 对应规则无法判定 → 该案例按「未匹配」处理，不猜测 |
| 5 | 调用方提供源码工程路径与报告地址（输出目录） | 核查规则需要源码工程路径；数据规则需要报告地址。两者即「数据范围硬约束」允许的全部输入 | 未提供时按数据范围硬约束处理：涉及缺失输入的规则「无法判定」→「未匹配」，不得自行搜索/推断路径外的数据源补齐 |

## 流程概览

```
子步骤 1：逐劣化源匹配 references/cases 场景（证据采集 → 逐规则判定 → 输出匹配/部分命中/未匹配）
子步骤 2：将匹配结果落盘为《案例匹配报告_<旧>_vs_<新>.md》（章节框架见子步骤 2）
```

## 子步骤 1：匹配 references/cases 场景

> **输入**：劣化源清单（8.1 的每一行，或调用方报告中的每个劣化 SO/HAP）+ 报告地址（输出目录）下的分析步骤产物 + 应用源码工程路径（仅当案例含核查规则时需要）。**所有输入均须落在「数据范围硬约束」允许的两类路径内。**
> **输出**：每个劣化源一条匹配结果：**匹配成功 / 部分命中 / 未匹配**（列表可为空）

遍历 `references/cases/` 目录下所有案例文档，对**每个劣化源**逐一与案例的「匹配规则」比对。匹配规则分两类，判定方式与证据来源不同：

> **匹配范围限定**：子步骤 1 **仅**遍历 `references/cases/` 目录下的案例文档。`references/` 目录下的其他文档（如 `arkts-leak-cases-and-faq.md`、各 workflow 的根因推断表等）**不纳入**子步骤 1 匹配范围——这些文档是深度分析阶段的参考，不含正式的「匹配规则」表格，不参与案例匹配判定。

### 1.0 案例库清点（遍历前置硬约束）

> **目的**：防止因「凭记忆 / 凭上一步报告的案例清单」选择性遍历导致案例文件遗漏。本步骤是子步骤 1 的前置门控，**未完成清点不得进入 1.1**。

**硬约束**：

1. **先 ls、后遍历**：进入子步骤 1 前，必须对 `references/cases/` 目录执行实际列举操作（`ls references/cases/*.md` 或等价 glob），记录**完整文件清单**（文件名 + 数量）。禁止凭上一轮分析记忆、凭对比报告 §8.1 的「案例库范围速览」、凭劣化源 SO 名推断案例文件清单——对比报告的案例范围可能本身就不完整（同源错误传播）。
2. **清单落盘到报告头部**：报告头部「生成依据」的案例库文档清单必须与 1.0 清点结果**逐一对应**——列出全部案例文件名，不得遗漏。清单文件数 < 实际目录文件数时，报告不得定稿。
3. **规则总数对账**：清点时同步统计每个案例文档的故障规则条数（文档内 `###` 级别案例标题数），记录「案例库总计 N 条故障规则，分布在 M 个文件」。报告速览的一句话结论必须使用该总数（如「案例库共 24 条故障规则，匹配成功 X 条」），禁止使用小于实际总数的数字。
4. **不涉及也要列行**：与本次劣化源无关的案例文件（如本次无 `libarkweb_engine.so` 劣化，ArkWeb.md 仍须列行），在速览「按案例规则看」表中标「❌ 不涉及」并注明原因（如「Top10 无 libarkweb_engine.so」）。不得因「不涉及」而省略列行——省略列行即无法与 1.0 清点对账，等于自证完整性。

### 1.1 证据采集（按规则类型取数）

> 「采集」仅指**读取**下表所列已落盘文件，禁止执行任何生成新数据的命令（见「数据范围硬约束」）。

| 规则类型 | 判定方式 | 证据来源 |
|---|---|---|
| **数据规则** | 判读报告地址下**已存在**的分析产物，无需新数据 | 步骤 2 对比报告（汇总表层级结构 / Top10 劣化 SO）、步骤 4 差分树 JSON / `<so>_diff.json` / 火焰图、步骤 5 `smaps_diff.json`、两版 HAP 解包列表（仅当调用方已将解包产物落盘在报告地址下时可用）、**`meminfo/hilog/hilog_*.txt`（ArkWeb 规则 2 的 `a` 值：grep CreateNWeb/OnDestroy 计数差值）** |
| **核查规则** | 读取源码工程路径下的应用源码核实 | 案例文档「检查要点」指定的源码位置；AI 按要点逐项核查，输出「发现缺陷 / 未发现缺陷」+ 证据 `文件:行号`。**`meminfo/window_dump/window_*.txt`（ArkWeb 规则 2 的 `b` 值：窗口 dump 中检索 Web 组件数）** |

### 1.1.1 产物精要与规则取数对照（AI 取数索引）

> 目的：让 AI 快速定位「哪条匹配规则读哪个产物、读哪个字段」。若报告地址下已生成 `产物说明.md`（产物全集说明），以其为准；本小节是**规则视角**的精要索引。

**报告地址（输出目录）典型布局**：

### 1.1.2 证据实测硬约束（本次案例分析教训，最高优先级）

**每一条判定证据（尤其是数据规则）必须以"匹配规则中指定的查看内容"为准、实际读取落盘产物，禁止凭经验、凭上一轮分析记忆、凭推断填写。**

> 口径说明：证据实测的对象 = **案例匹配规则明确指定要查看的内容**（如 taskpool.md 规则 2「差分树中 name 含 `napi_deserialize` 的节点 delta_mb > 0」、dma.md 规则 2 的 SurfaceBuffer 关键帧 .db 检索（`data_dict` + `native_hook_frame` 按帧名子串检索；DMA 型 SO 本身无 native heap 聚类树/火焰图，属数据本质限制，不得据"火焰图未生成"判 ❌）、hap.md 的 xlsx size 单元格等）。规则指定查看哪个产物字段，就对该字段实际检索；规则未指定查看项的帧名仅作调用链展示，不参与案例判定证据，不必逐一实测。

真实教训：某次分析中，上一轮（不同场景/不同案例页）差分树出现过 `napi_deserialize` 帧，本轮是 TaskPoolGrowthCase（http 任务），差分树**根本没有**该帧——但 AI 把上轮记忆写进本轮证据表，判定案例规则 2「通过」，导致案例误判为「匹配成功」。实测 grep 差分树 JSON 后才发现 0 匹配。

硬约束（违反任一条即证据无效，须重跑）：

1. **规则指定的查看项要"先实测、后落笔"**：在写证据前，对匹配规则指定的产物字段执行**实际读取命令**（如 `grep -c "napi_deserialize" <so>_diff.json`、`grep -o 'napi_[a-z_]*' <so>_diff.json | sort | uniq -c`、读取 xlsx 单元格、读 flame HTML 帧名），拿到真实输出后才写证据。
2. **未实测 = 证据不存在**：规则所需的关键帧/字段如果在产物中检索不到，该规则按「❌ 不通过」判定，**不得**写"含 xxx 帧"或"xxx 占用增加"等字样。检索结果为 0 时如实写"grep 0 匹配，该帧不存在"。
3. **证据必须可复核**：证据列必须写明**产物文件路径 + 实际检索命令 + 真实输出**（如「`native_heap/libtaskpool.z.so_diff.json` grep `napi_deserialize` → 0 匹配，差分树中无该帧」），不得只写结论不写依据。
4. **禁止跨轮/跨场景套用产物**：差分树、火焰图、smaps 等产物每次分析独立生成，上一轮或另一场景（另一案例页/另一采集）的帧名、数值**不得**默认为本轮存在。引用产物证据前必须重新实测本轮产物。
5. **AI 整合时的自我核查**：把步骤 3/4/5 agent 返回的结论写入报告前，对其中引用的关键帧/数值在落盘产物中 grep/复查一遍，确认 agent 结论与本轮产物一致；不一致则以实测为准。

### 1.1.3 规则类型不可替代硬约束（本次案例分析教训，与 1.1.2 同级）

> **真实教训**：ArkWeb.md 案例一规则 2 是 **hilog 核查规则**（用 `hilog | grep -E "CreateNWeb|NWebImpl::OnDestroy"` 分析存活组件数）。AI 未执行 hilog 命令，用**源码核查**（发现 `preCreate(6)` 调用）替代了 hilog 数据规则，判定规则 2「通过」——这是错误的。hilog 数据规则要求实际读取 hilog 日志产物，源码核查不能替代。

匹配规则分两类（见 1.1 证据采集表），两类规则的证据来源不同，**严格不可互相替代**：

| 规则类型 | 证据来源 | 禁止的替代方式 |
|---|---|---|
| **数据规则** | 报告地址下**已落盘**的分析产物/采集数据（对比报告/xlsx/diff.json/hilog 日志等） | ❌ 不得用源码核查替代（即使源码中明确存在对应调用） |
| **核查规则** | 应用源码工程路径下的源码 | ❌ 不得用产物数据替代（即使产物中存在对应字段） |

硬约束：

1. **数据规则只能用产物数据判定**：案例文档将某条规则标注为「数据规则」时，必须读取对应的落盘产物（hilog 日志/xlsx/diff.json/smaps_diff.json 等）执行判定。产物中检索不到所需数据时判「❌ 不通过」或「无法判定」（按 1.2 处理），**不得**用源码核查结果（如"源码中存在 xxx 调用"）替代产物数据。
2. **核查规则只能用源码判定**：案例文档将某条规则标注为「核查规则」时，必须读取应用源码执行判定。源码中检索不到对应代码时判「❌ 不通过」或「无法核查」，**不得**用产物数据（如"火焰图中存在 xxx 帧"）替代源码核查。
3. **规则类型判定依据**：案例文档中每条规则的类型由文档自身的标注决定（如 ArkWeb.md 规则 2 标注「核查规则」、规则 3 标注「数据规则」）。AI 不得自行改变规则类型标注。

### 1.1.4 规则内子条款完整性硬约束（本次案例分析教训，与 1.1.2/1.1.3 同级）

> **真实教训**：worker.md 规则 3 标题为「同一任务 worker 数量 ≥ 8」，源码中 `WORKER_COUNT=8` + `for` 循环 `new worker.ThreadWorker(WORKER_SCRIPTS[i])`。AI 见 `WORKER_COUNT=8 ≥ 8` 直接判「命中」——但规则 3 正文含**统计口径子条款**，明确区分「同一 script 在循环中创建 N 个实例（口径 a，计 N）」与「不同 script 各 1 个 worker（口径 b，不累加）」。`WORKER_SCRIPTS` 是 8 个不同 script 路径的数组，属口径 b「多任务并行」，同一任务实例数 = 1 < 8，规则 3 **不通过**。AI 只看了规则标题条件（≥8），忽略了正文中的口径区分子条款，导致案例误判为「匹配成功」。

> **与前两条约束的区别**：1.1.2 防「证据编造」（规则指定的查看项没查就写"通过"）、1.1.3 防「规则类型混淆」（数据规则用源码核查替代）。本条防的是**第三种错误**：证据查了、规则类型也没搞混，但规则正文含**口径区分/例外子条款/统计方法论**时，只看了规则的标题条件（headline condition）就判通过，**忽略了正文中限定该条件如何适用的子条款**——等于把一个含例外的规则当成了无例外的规则来执行。

**硬约束**：

1. **逐条规则必须通读全文，不得只看标题/加粗条件**：案例文档的每条匹配规则可能包含标题条件 + 统计口径 + 例外条款 + 降级说明等子条款。判定前必须**通读该条规则的全部正文**，识别其中是否含以下子条款类型：
   - **统计口径子条款**（如「同一任务实例数 = …」「不同 script 各计 1 个但不累加」）——定义标题条件中的关键术语如何计数
   - **例外/排除子条款**（如「多任务并行属合理架构选择，不属本案例」「新版替换写法不构成数量增加」）——定义标题条件的适用范围边界
   - **降级子条款**（如「仅单版源码无法做版本 diff 时，本规则按无法判定处理」）——定义规则在特定条件下的降级处理

2. **所有子条款必须逐项满足**：标题条件满足（如 `WORKER_COUNT=8 ≥ 8`）**不等于**规则通过——必须同时检查所有口径区分/例外子条款。任一子条款不满足（如属口径 b「多任务并行」导致同一任务实例数 < 8），该规则按「❌ 不通过」判定。

3. **子条款判定须附证据**：证据列须写明对**每个子条款**的核查结果（如「口径 a/b 判定：WORKER_SCRIPTS 为 8 元素数组，循环内 `WORKER_SCRIPTS[i]` 随 i 变化 → 口径 b 多任务并行 → 同一任务实例数 = 1 < 8 → 规则 3 不通过」），不得只写标题条件的核查结果。

4. **高频误判场景清单**（判定前逐项自查）：
   - **worker.md 规则 3**：`WORKER_COUNT=8` + 循环创建 → 先查 `new worker.ThreadWorker()` 传入的是同一个 script 路径（口径 a，同一任务）还是不同 script 路径的数组元素（口径 b，多任务并行）；口径 b 时同一任务实例数 = 1 < 8，规则 3 不通过
   - **dma.md 规则 2**：SurfaceBuffer 关键帧检索 → 先确认目标 SO 是 DMA 型（type_name 含 DMA）还是 malloc 型；DMA 型 SO 按 SO 名聚类必然报"无匹配调用栈"属数据本质限制，不得据"火焰图未生成"判 ❌
   - **taskpool.md 规则 2/3**：源码 diff 新增调用 → 先确认是「新增 taskpool.Task/taskpool.execute 调用」还是「存量调用点参数变化」；两者对应的案例不同（案例二要求新增、案例三要求多点新增），不得混用

### 1.2 逐规则判定

- **匹配成功**：该案例**所有**匹配规则（含核查规则）全部通过。
- **部分命中**：数据规则全过、但核查规则未确认（未发现缺陷 / 无源码工程无法核查）。**不得输出根因结论**——部分案例以核查规则为结论性门控（如 dma.md 规则 3：数据命中可能只是合理的可见渲染增长）。按「未匹配」处理：8.1 根因列写「未匹配案例库，需人工核查」，同时**保留已命中规则清单**供人工核查参考（这是数据记录，不是根因推测）。
- **未匹配**：任一数据规则不通过，或案例与该劣化源维度不符（如 SO_SIZE/HAP 劣化源不会命中 DMA 案例），**或规则所需数据不在允许的两类路径内（无法判定，见「数据范围硬约束」）**。无法判定时同样保留可判定的数据记录并标注缺失证据项，但不得为补齐而采集。

> ### ⚠️ 禁止引入规则之外的判定标准（本次案例分析教训）
> **真实教训**：ArkWeb.md 案例三「离线 Web 组件未复用/释放」三条规则全部通过（源码中确实存在未复用/未释放的反模式），但 AI 额外引入了规则之外的主观判断——"冷启动阶段主要矛盾是预创建，累积型增长需运行时触发"——将匹配成功误判为未匹配。案例三的规则只检查源码是否存在反模式（未调 loadUrl/dispose），不要求运行时已触发累积。
>
> **硬约束**：
> 1. **判定只看规则是否通过**：案例文档定义了明确的匹配规则（通常 2-3 条），判定结果**仅**由这些规则的通过/不通过决定。AI 不得额外引入规则之外的判定标准（如"主要矛盾"、"运行时是否触发"、"冷启动阶段"等主观判断）。
> 2. **规则之外的发现不改变判定**：即使 AI 有合理的业务判断（如"冷启动阶段预创建是主因，未释放是次要问题"），也不得据此改变案例规则的判定结果。业务判断可写入报告的"备注"或"根因关系图"，但不影响匹配判定。
> 3. **全部规则通过 = 匹配成功**：只要案例文档的所有匹配规则全部通过，即判定为「匹配成功」，无例外。

### 1.3 输出匹配结果列表

每个匹配成功的场景一条，含：

- 案例出处（如「dma.md 一、不可见 XComponent SurfaceBuffer 未释放」）
- 命中的匹配规则（核查规则须附核查结论与证据 `文件:行号`）

未匹配/部分命中时输出对应记录（部分命中附已命中规则清单），标注「未匹配案例库场景」。**未匹配/部分命中的劣化源不得给出无依据的建议**。

> 案例库匹配范围**仅限** `references/cases/` 目录

## 子步骤 2：输出案例匹配报告

> **输入**：子步骤 1 匹配结果列表
> **输出**：`<输出目录>/案例匹配报告_<旧版>_vs_<新版>.md`（与对比报告同目录、同 `<旧>_vs_<新>` 命名风格，即 1.1.1 布局中的「本流程自身的输出产物」）

将子步骤 1 的匹配结果整理为一份完整**匹配报告**落盘——只含匹配结果与判定证据，**不含优化建议/修复方案**（修复动作由 SKILL.md 步骤 7 的优化 SKILL 或人工基于匹配结果进行）。报告格式以历史产出（`output_fresh/优化方案_7.1.4.32_vs_7.3.3.32.md`）为章节基准改造而来（删优化建议章、速览只留匹配维度），章节框架固化如下：

### 报告章节框架

| 章节 | 内容 | 来源 |
|---|---|---|
| 头部 | 标题「案例匹配报告：<旧版> vs <新版>（冷启动内存对比）」；生成依据（本流程 + 案例库文档清单）；输入劣化源清单出处（对比报告 §7.1）；证据范围声明（仅「数据范围硬约束」两类路径，未现场采集） | — |

| 一、案例库匹配结果总览（按故障规则分章） | 每个案例故障规则一节（节结构见下）+ 章末两节（未覆盖维度、汇总表） | 子步骤 1 |
| 二、流程合规声明 | 证据来源两类路径清单；部分命中/未匹配的处理方式；核查规则受限说明（如源码工程非劣化应用真实源码）及可复匹配条件 | — |

### 第一章「按故障规则分章」的节结构

每个案例故障规则（如 hap.md 规则一/规则二、dma.md 规则、imageknifepro.md 规则）单独一节，固定四要素：

1. **故障模式**：案例模式描述的一句话概括，与案例文档表述一致
2. **匹配规则**：规则条数与案例文档一致；呈现上可与要素 3 合并为一张表（`# | 规则 | 类型[数据/核查] | 判定 | 证据`），避免规则表与证据表两张表重复
3. **判定证据**：每条规则给出 ✅/⚠️/❌/无法核查 + 具体证据（产物文件 + 字段/数值，如 smaps_diff.json 的 `is_new`/size、xlsx 行值、grep 结果）；「SO 级匹配成立但劣化源登记维度不同」的情形须附**匹配作用域说明**（匹配结论覆盖哪部分差值、哪些维度仍无案例覆盖）
4. **结论**：匹配成功（对应劣化源编号）/ 部分命中（保留已命中规则清单）/ 未匹配 + 依据

排序与篇幅（可读性要求）：

- **按结果分组排序**：章内小节依次为 匹配成功 → 部分命中 → 未匹配（同组内按案例文档顺序），小节标题附结果标记（✅/⚠️/❌）
- **篇幅裁剪**：匹配成功/部分命中的小节保持全量四要素；未匹配的小节可压缩为紧凑表格（规则 | 判定 | 证据，一行一条）+ 一行结论，故障模式一句话带过

章末固定两节：

- **案例库未覆盖维度（无故障规则可比对）**：表格汇总（# | 劣化源 | 差值 | 维度 | 数据记录/深度分析指引），标注按未匹配处理
- **匹配结果汇总（对应 §7.1 劣化源清单）**：表格（# | 劣化源 | 差值(MB) | 匹配结果 | 命中章节），与劣化源清单一一对应

### 格式硬约束

- **速览先行**：头部声明后必须有「速览」层（一句话结论 + 按案例规则看 + 按劣化源看），先给匹配结论、再展开详细判定
- **一个故障规则一节**：`references/cases/` 新增案例文档后，第一章按此粒度自动扩展，无需改本流程（速览的「按案例规则看」表同步加行）
- **证据可复核**：判定证据须写明产物文件与数值，可直接回查
- **只给匹配不给建议**：匹配报告**不含优化建议/修复方案**——任何条目（含匹配成功项）下均不得给修复建议、优先级排序或泛化建议；修复动作由 SKILL.md 步骤 7 优化 SKILL 或人工基于匹配结果进行。未匹配/部分命中仅保留数据记录（部分命中附已命中规则清单 + 缺失证据项）
- **引用不扩展**：匹配成功条目引用案例文档表述时保持一致；引用产物自动结论（如 smaps_diff.json 的 suggestion）时注明出处
- **案例库完整性自检**：报告定稿前，将速览「按案例规则看」表的行数 + 第一章小节数与 1.0 清点的案例文件数 / 规则总数对账。对账公式：速览表行数 = 案例库故障规则总数（1.0 统计值）。不等则回溯补齐遗漏的案例文件后再定稿。此自检与 1.1.2「证据实测硬约束」同级，违反即报告无效
