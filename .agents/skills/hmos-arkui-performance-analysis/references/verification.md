# 常用性能验证

用于选择与当前问题对应的验证方法。Trace工具用法和事件含义见[Trace指南](trace-guidance.md)，按本次验证目标查阅。

## 验证方法的选择与表达

先说明本次建议预期减少哪段工作，再给适用的方法。日志与Trace都能验证时中性并列，说明各自目标供开发者选择；只有一种适用时给一种。每种方法简洁写清记录/打点位置、触发动作、观察对象、比较窗口和预期，共同比较条件只写一次。固定数据规模、设备、业务动作与缓存条件，多次比较；未实测不填收益数字。通常给当前问题的操作与指标即可，采集命令和通用工具教程按需查阅，不重复展开。

- 日志/计数用于实际创建、复用、任务执行、缓存命中或载荷变化。分清首次准备与后续操作，不把aboutToAppear次数当作复用次数。验证最终采用的方案；已删除路径的零计数只说明该路径消失，不能代替新驱动的播放、控停或资源释放验证。
- Trace用于当前机制确有对应事件或可包围实际代码的成本。CPU调用栈可辅助定位；不假设存在跨版本通用的专有标签。
- 整体响应时间可衡量整体体验，但混入数据准备、IO或其他工作时，不能单独归因某次复制或构建。相同输入下解释具体减少的工作，不为放大现象擅改数据规模。

## 如何定位动作后的更新帧

当前同步计算比较包围该调用的Duration。后续UI更新先标记实际状态赋值/数据提交，在Trace搜索该业务点、选中放大，以时间对齐应用UI线程，定位实际处理更新的完整ReceiveVsync区间。动作发生在帧外时从其结束向右找适用更新帧；帧内提交则判断当前帧是否已处理。多个帧或onIdle续后执行时分别定位实际窗口，不能只看请求后的第一帧。

## 新增业务打点的写法

需要新增Trace时给出当前函数中的实际插入位置、成对调用与匹配参数，例如：

```ts
import { hiTraceMeter } from '@kit.PerformanceAnalysisKit';
hiTraceMeter.startTrace('APP:ActualWork', 1);
try {
  // 此处替换为当前需要比较的真实同步调用。
} finally {
  hiTraceMeter.finishTrace('APP:ActualWork', 1);
}
```

名称按业务命名。标记同步段时在await挂起前结束，续体另起；跨await区间含等待，不能当作CPU耗时。节点ID、参数和事件可见性以实际录制为准，缺事件先核对开关、版本与窗口。

## 观察窗口

启动创建量包含页面开始构建到关联首帧的同一窗口；首次有效内容、完整内容就绪分别计时。转场比较首次反馈、动画长帧与完整就绪，骨架出现不等于加载完成。滑动固定路径和缓存条件；动画按目标比较触发同步调用或完整动画窗口，不能把二者混同。各机制的专用指标和适用限制随对应规则给出。
