# 数据传递成本与同步语义

## 前提与机制

状态管理 V1 的 @Prop 建立父到子单向同步；子组件可以修改本地值，修改不回传父组件，父数据后续更新可覆盖本地修改。对象传递涉及复制成本，但 @Prop 本身不是性能缺陷。基本值、小而有界的数据、必要的本地编辑隔离都是正常情况。@ObjectLink 则接收父组件 @Observed 类对象的引用，建立双向同步：子组件的修改会直接作用于父组件持有的同一对象，没有本地副本隔离。

## 检查方法

追踪父传值、子读取、子写入及再次同步路径，再看对象大小、实际更新频率和只需要哪些字段。数据未知时不能仅凭类型名 LargeData 定位成本。把 @Prop 改为 @ObjectLink 不是等价替换：同步从父到子单向变为双向，子组件修改会写回父组件共享对象，本地编辑隔离与"父更新可覆盖子修改"的行为同时消失，替换建议必须核对读写关系；跨层 Provide/Consume 不能仅因层级多就改成 State/Link。

## Bad case

```ts
class MessageBundle {
  title: string = '';
  history: string[] = [];
}
@Component
struct TitleView {
  @Prop bundle: MessageBundle = new MessageBundle();
  build() { Text(this.bundle.title) }
}
```

前提：父组件频繁传入 history 含大量条目的新对象，而该子组件只显示 title，也不读写 history。可指出不必要传递大数据的风险，建议先只传 title；没有数据规模和频率证据时不能量化成本。

## Good case

```ts
@Component
struct TitleView {
  @Prop title: string = '';
  build() { Text(this.title) }
}
```

父组件对应传 `TitleView({ title: this.bundle.title })`，保留所需单向同步。若子组件还需要历史数据或整体快照，就不能删掉所需内容。

另一个合理反例是输入框编辑本地副本、取消后父值保持不变：即便复制有成本，也不能无条件替换为 @Link/@ObjectLink。可以讨论更小编辑模型、明确提交事件等方案，但须保留取消/提交和父更新行为。

## 建议与验证

先缩小数据载荷和不必要更新；只有确认业务允许共享引用、满足装饰器类型条件（@ObjectLink 需父侧传入 @Observed 类实例）且接受单向变双向的语义影响时，才讨论引用传递。不能把复杂 native 对象复制失败的问题统称性能问题，也不能承诺 @Prop 对所有类型完全保真。

按实际读写路径在建议中保持父更新、子编辑隔离和数据身份，默认不另列功能测试清单。性能验证固定原有数据规模与更新节奏；允许比较整体响应，但不能单凭包含父侧准备的总耗时归因复制收益，也不为放大现象擅自提高数据规模。

输入缺父组件或写操作时列最小缺口，仍分析现有读取；不以 Trace 取代同步方向核查。

## 打点与预期变化

观察方式：本规则不假设存在固定、跨版本可用的 @Prop 深拷贝框架标签。使用 CPU 调用栈确认父子传参/复制工作，必要时增加覆盖实际同步路径的业务打点或载荷计数。只传所需字段后，预期进入子组件的无关载荷及对应复制工作减少；父侧仍构造完整对象时，该准备成本仍然存在。不能用覆盖父数据生成和多项业务的总区间直接宣称传递成本已下降，也不能编造 `PropCopy` 等内置打点。
