# 性能分析报告与交付

报告按问题组织。每个成立的问题应包含以下信息，按实际分析写清，不把预期收益写成实测结果：

- **问题位置：** 给出真实文件路径、行号或代码片段边界，定位到产生问题的代码。
- **代码事实与条件：** 说明触发动作、相关代码行为及业务、版本等成立条件，区分已有事实与需要核实的内容。
- **性能机制：** 解释这些行为如何增加创建、刷新、计算、布局或绘制等工作，以及与当前现象的关系；功能语义问题按实际数据流说明。
- **修改建议：** 给出适合当前工程版本和条件的具体方案。需要修改代码且信息充分时，默认提供可定位、可直接采用的最小diff或可替换代码，不只列接口名或口头步骤；不强制枚举所有替代路线。
- **语义影响：** 说明方案对数据、状态、交互、布局、时序及资源的相关影响，明确需要保留的业务行为与必要代价。
- **预期收益：** 说明预计减少哪部分工作、改善哪个阶段；估算注明依据，未实测不写成已验证结果，功能修复不虚构性能收益。
- **验证方法：** 写清复现动作、观察对象或指标、修改前后的比较条件和预期变化。按目标选择日志、计数、视觉观察或Trace；已有验证结果时说明结果，未执行则如实注明。

修改代码按改动规模选择一种形式：

- **小改动：** 用diff展示原写法与新写法，保留定位所需的上下文。
- **局部修改：** 给出可直接替换的类或方法，标明其余保留部分，不复制无关的整页ETS。
- **多处联动：** 将必要导入、字段、方法、回调和调用处一起给齐，参数与生命周期衔接完整，不留给开发者自行拼接关键实现。

工程代码使用真实文件路径和修改位置；纯片段按已有类或方法定位，不编造文件名、行号。信息不足时说明缺口，只给可确认部分；仅需核对体验或无需修改时，不为展示代码制造整改。

没有成立问题时，简短说明已分析范围与必要限制；参数核对直接结合当前动效或交互意图给建议，不为凑报告制造整改。

默认在对话中交付。用户要求报告文件时，按指定路径或工程报告约定生成Markdown，写入后核对内容，最终回复给出摘要和可点击的报告链接，不重复粘贴全文。
