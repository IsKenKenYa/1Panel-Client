# 首屏图片加载与尺寸占位

## 前提与机制

首屏多张大图同步加载有主线程工作风险；从宽高显示属性不能推断资源真实像素尺寸。

首页初始图片异步加载完成后，若组件或 FlowItem 从临时尺寸改为实际尺寸，可能使所在容器重新布局。业务已提供图片比例或稳定条目尺寸，却仍在完成回调中逐项改变高度时，应检查这部分可避免的布局工作。默认异步加载并不代表布局成本已全部消除。

小尺寸本地图标可适合同步；官方案例明确允许这种选择。不能仅因 syncLoad(true) 报错。

已设置正确比例或稳定占位、加载完成只更新显示状态的代码，无需再改；资源比例未知且自适应高度属于业务要求时，不能把一次必要布局认定为冗余。

## 检查方法

1. 读取 syncLoad 设置、图片真实来源与像素尺寸、首屏数量、是否本地、显示和占位要求。只看到资源名 4k、icon 或 URI 不能视作尺寸事实；无法读资源时确认真实尺寸与来源。
2. 对不适合同步的资源评估默认异步加载，说明图片出现时机与占位效果；同时检查数量与按需创建，不把所有问题都归为图片。
3. 跟进图片加载前后的组件及条目尺寸、尺寸来源与完成回调。已知比例时，在首次构建中依据实际可用宽度确定高度，或使用符合业务要求的稳定尺寸占位。
4. WaterFlow 同时核对 FlowItem 的高度，避免仅固定 Image 却仍让外层条目变化。不要为统一尺寸裁掉必要内容；未知比例且必须自适应时，保留必要布局变化。

## Bad case

### 多张大图同步加载

前提：资源为 3840×2160 本地图，首屏批量加载，业务允许异步显示。显示 100vp 不代表只解码 100 像素。

```ts
Image($r('app.media.photo')).width(100).height(100).syncLoad(true)
```

### 已知比例仍在加载完成后改变尺寸

前提：图片比例已知为 2:1，显示宽度固定为 200vp；imageHeight 初始为 40vp，外层条目随图片高度变化。

```ts
Image($r('app.media.preview'))
  .width(200)
  .height(this.imageHeight)
  .onComplete(() => { this.imageHeight = 100; })
```

## Good case

### 按需异步加载

```ts
Image($r('app.media.photo')).width(100).height(100)
```

使用默认异步加载，保留原有显示尺寸和占位要求。24×24 本地图标数量少且需要同步显示时，可保留原写法。

### 首次构建即保留正确尺寸

```ts
Image($r('app.media.preview')).width(200).height(100)
```

对应上述固定宽度和已知比例，不再由完成回调修正高度。可用宽度变化时，按实际宽度与比例计算；外层条目也要保持正确占位，不能照搬固定值。

## 建议与验证

核对图片完整显示、尺寸占位、首屏要求和状态变化；实际解码/缓存耗时必须有运行数据才可量化。
代码与条件足够时直接给建议，不要求 Trace。必要信息已检查仍无法解释持续慢，再使用 [Trace 指导](../trace-guidance.md) 选择相关阶段。

## 打点与预期变化

对应打点：观察 `CreateImagePixelMap`，按资源、时间窗及线程关联到首帧的 `FlushLayoutTask`；必要时结合 CPU 调用栈确认同步解码或等待。改为默认异步后，预期 UI 首帧布局路径中的同步图片工作/等待减少，解码可能转移到后台，不能要求四张图片的总解码次数减少。冷缓存与热缓存分别比较；缓存命中时可能没有新的解码事件，不可据此推断图片没有加载或开销为零。

尺寸占位场景从首页首次展示观察到初始图片完成，关联完成回调、目标图片/条目的尺寸变化与 Measure/Layout。提前设置正确占位后，预期由加载完成引起的尺寸变更和后续布局减少；图片仍需显示，初次布局仍存在。回归不同屏幕宽度、图片完整显示和条目排列，不能只删除回调而保留错误尺寸。首帧之后的布局计入初始内容加载过程，不累计到首帧耗时。
