# 页面分阶段展示与目标页骨架

## 前提与机制

启动首页或转场目标页已有可显示的标题、导航、缓存内容或关键操作，但整个页面被一个 ready 状态挡住，直到非关键区域数据全部返回才创建。业务允许这些区域稍后显示时，可提前呈现已就绪内容，缩短首次有效内容的等待。启动与转场共用本文件。

检查 ready 的写入位置、实际等待项和各区域依赖，不凭 Promise.all、async 或变量名称判定等待不合理。必要权限、身份校验、必须一致展示的数据尚未就绪时，不应提前显示依赖它们的内容。

## 检查方法

1. 跟进首页构建条件和数据完成回调，确认哪些区域必须同时就绪、哪些可以独立展示；将整体等待改为按区域就绪更新。
2. 保留轻量的关键内容，后续区域用骨架或简单占位明确加载状态，并预留合理尺寸；已就绪内容不反复销毁重建。只有业务允许时才分阶段，不机械要求每个首页加骨架。
3. 保留加载失败、重试、空结果和离页后的结果有效性。骨架不接收真实操作，也不伪装业务已完成；正式内容出现后，显示与事件对应当前数据。
4. 区分数据等待与同步计算。骨架不能让 UI 线程中的复杂计算自动转到后台，也不能让网络请求更快；同步工作的处理见[生命周期同步耗时](lifecycle-work.md)。

## 列表进入详情时的转场顺序

**Bad**：点击记录 → await 真正异步的详情请求 → 请求完成后才切换详情页。主线程不一定阻塞，但业务允许先出现的目标页框架和返回操作仍被推迟。

**Good**：点击记录 → 先进入确定的详情页并显示框架/骨架 → 请求完成后更新正文。Navigation/Router 在真实目标路由中处理加载状态；单宿主条件内容页则先改变显示分支，不为骨架新增无关路由。

返回后再进入另一条记录时，用当前 ID/请求版本防止旧结果覆盖；加载、错误、重试、空内容均保留。骨架尽量贴近最终区域尺寸，目标页导航与返回无需等待正文；必要鉴权和决定去向的数据仍按业务完成后再进入。

## Bad case

前提：首页标题和关键内容已就绪，recommendations 是允许稍后显示的非关键区域。

```ts
// 整个首页等待推荐区
if (this.recommendationsReady) {
  this.header()
  this.primaryContent()
  this.recommendations()
}
```

## Good case

```ts
this.header()
this.primaryContent()
if (this.recommendationsReady) {
  this.recommendations()
} else {
  this.recommendationsPlaceholder()
}
```

header、primaryContent 不再等待非关键推荐区。recommendationsPlaceholder 是业务提供的轻量占位 Builder，保留合理尺寸和加载提示；推荐区域还需处理原有失败与重试状态。

## 建议与验证

合理反例：关键内容已先显示，其他区域已有独立加载与失败状态；或首页必须等待必要校验完成才可展示。当前没有相应问题时，不要求增加分阶段控制。

分别记录首次有效内容显示与初始内容完整就绪的时间，转场另记动画开始和结束，验证加载中、成功、失败、重试及离页场景。预期关键内容先显示，非关键区域随后正确更新；完整内容就绪时间可能不变，不能把占位出现时间当作全部内容加载完成。

## 打点与预期变化

用状态变更、目标子树创建、相关帧与建议新增的业务打点关联展示过程。框架首帧可能早已显示空白或占位，不能仅由 ready 提前推断系统冷启动首帧加快。需要运行证据时使用[Trace 指导](../trace-guidance.md)。

## 依据
