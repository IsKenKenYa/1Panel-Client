# Trace 采集与观察指导

按当前验证目标查阅相关工具与事件说明，常用比较口径见[验证方法](verification.md)。

本文件只生成开发者自行执行的指导，不启动设备、GUI或采集命令，不读取/解包/转换Trace，不声称自动归因。缺代码先补最小材料，不能把采集教程当作必须附带的回答。

## 选择一条路径

- 已有 DevEco Studio Profiler：按该版本官方启动/CPU 分析指导创建适用采集会话。界面名称不确定时给官方文档入口和要确认的信息，不编造菜单。
- 已有 SmartPerf：按已安装版本的系统 Trace 捕获/离线导入指导操作。
- 熟悉命令行且设备允许：使用 hdc/hitrace，先核对设备支持的标签与语法。不要求同时安装三种工具。

## 八项采集指导

1. 记录工具版本、系统版本、设备、应用包名、构建配置和数据规模；不同版本支持项可能不同。
2. 确认开发者能连接目标设备；多设备时显式选择目标。采集由开发者操作。
3. 根据待验证的阶段选择采集项；用该设备支持列表核对 UI/图形/调度相关项。app 示例标签并非全部框架事件的充分配置。
4. 写明目标场景、前置状态、复现动作和结束观察点。组件场景明确状态修改、列表复用或创建销毁；启动场景区分冷启动首帧、首页初始内容就绪与启动前置页进入首页，只切回已有进程不能自动当冷启动。转场记录源页/目标页、缓存与池状态、跟手/离手阶段，覆盖进入、返回和快速反向。
5. 在触发目标动作之前开始录制，覆盖动作前后与问题区间；启动场景按疑点覆盖首页首次展示、初始图片和数据完成，有前置页时包含准备首页与进入首页的过程。
6. 复现后及时结束；缓冲区可能覆盖最早事件，避免无边界长录制。
7. 按工具导出原始数据并保留元信息、复现动作/时刻；不要只保存截图丢失上下文。
8. 检查目标进程、时间窗和事件是否在录制内；缺失时先修采集配置/时机，不能开始猜根因。若主动改变调试开关，记录原值并在结束后恢复。

### 命令行示例

[hitrace 命令文档](https://gitcode.com/openharmony/docs/blob/master/zh-cn/application-dev/dfx/hitrace.md)提供下列文本模式序列。使用前核对 `hitrace -h` 和 `hitrace -l`，确认标签存在；示例 app/graphic 不是通用完整采集配置。若当前环境不支持，应改用该版本官方路径，不擅自替换参数。

```sh
# 主机，进入目标设备；多设备先按 hdc 文档选定目标
hdc shell
# 以下在设备 shell 中
hitrace -h
hitrace -l
hitrace --trace_begin -b 204800 app graphic
# 此时开发者执行目标动作并复现问题
hitrace --trace_dump -o /data/local/tmp/arkui.ftrace
hitrace --trace_finish
exit
# 以下回到主机
hdc file recv /data/local/tmp/arkui.ftrace ./
```

204800KB 是官方示例缓冲区，不是固定要求；根据设备与录制时长选取支持值。dump 时点应在问题区间结束后；finish 用于结束采集。若需要区分调度等待，先核对并启用该版本支持的调度采集项，不假定以上示例已具备。

## 六项基本查看

1. 在支持该格式的 Profiler/SmartPerf 中导入。Profiler 可用官方文档所述 Open File 入口，具体位置以版本为准。
2. 找应用进程和主/UI线程，不把其他进程的工作归给应用。
3. 根据复现动作框选问题时间段；采集起点不是启动或目标交互的起点。
4. 放大长区间，查看名称、持续时间、单位、子事件及可用线程状态。父子重叠时间不可直接相加。
5. 按本次疑点选择下方相关打点。事件可能带 H: 和动态参数，搜索前缀后核对上下文，不要求完整字符串匹配。
6. 记录区间、截图、事件名、持续时间和观察分支，供进一步人工定位。没有可靠送显关联，不能把布局结束/应用提交作为首帧已上屏。

## 组件问题观察

| 疑点 | 参考名称/工具 | 看什么 | 分支与限制 |
|---|---|---|---|
| 状态影响范围大 | 目标更新帧的完整 `ReceiveVsync` 区间；按需补充 `ViewPU.viewPropertyHasChanged` 或 `CustomNodeUpdate` | 先比较写入后目标更新帧的总处理耗时，再按需观察状态名后第一个数字所表示的依赖数量；详见[状态更新验证](component/state-observation.md#v1-状态通知参数与后续更新验证) | 预期无关更新工作减少，整体耗时是否缩短由完整帧区间的前后比较确认；依赖数量按实际绑定推导，运行时 ID 从录制读取 |
| 复用回调慢 | `aboutToReuse` 搜索前缀 | 组件、区间频率、参数/同步/用户回调子工作 | 区间含参数和状态更新，不能全归给用户回调；短单次也需看频率 |
| 重复创建与复用成本 | 实际创建/复用回调日志；对应更新帧的完整 `ReceiveVsync` | 相同动作下的创建/复用次数及帧处理耗时 | 日志验证重复创建是否减少，Trace 比较整体耗时；首次创建与后续复用分别比较，两种方法按条件提供，供开发者选择 |
| 列表/属性计算 | 文档中的 `Builder:BuildLazyItem`、布局区间及应用已有业务打点 | 问题时间窗中工作次数与长区间 | 无业务打点/调用证据只能定位阶段，不能唯一映射到某行代码 |
| 帧回调耗时 | onFrame/onIdle 的函数计数、CPU 调用栈或新增业务打点 | 两个回调的单次与每帧累计工作 | 将复杂计算与同步 IO 移出 UI 帧路径后，相关回调耗时应减少；必要提交和结果有效期仍正确 |
| BuilderNode 重复构建 | new/build/update/dispose 的函数计数或新增业务打点 | 同结构参数变化是否仍重建节点 | 缓存并 update 后，首次创建仍存在，后续 build 应减少；回归当前参数显示与最终释放 |
| 跨父组件与页面复用 | 池命中/未命中、存活数量及组件创建计数 | 父组件切换是否仍导致池销毁或持续新建 | 后续同类型切换应增加缓存命中、减少初次创建；内存有界，原挂载解除与新参数更新正确 |
| 修改后仍慢 | 同场景前后可比的录制 | 相同数据、动作和版本下的阶段分布 | 相关区间已改善时继续查剩余阶段；不得为了维持原结论强行归因 |

### 状态关联的补充路径

对状态范围问题，可按官方状态变量组件定位文档：打开页面 → 获取窗口 ID → 查看自定义组件树和节点 ID → 查看该组件状态变量 → 核对同步对象和关联组件。具体命令参数依版本核对，不把 V1 工具输出直接解释为所有 V2 场景。

## 启动问题观察

首页加载、初始隐藏子树等创建成本问题，可同时给出以下两个观察窗口，分别比较修改前后相同启动条件下的多次 Duration：

- **页面加载耗时**：在应用 UI 线程搜索 `load page:`，按首页实际路由筛选，例如 `load page: pages/Index`，选中完整区间读取 Duration。页面路径来自当前工程，事件中的运行时 ID 从实际录制确认。该区间可用于观察页面加载期间的初始化和构建工作，包括首个 ReceiveVsync 之前的工作。
- **首页首帧处理耗时**：定位与该首页首次显示关联的 `ReceiveVsync`，选中完整区间读取 Duration，观察首帧处理工作。页面加载区间与帧区间分别比较，存在重叠时不直接相加。

| 疑点 | 搜索名称/前缀 | 看什么 | 结果分支及下一步 |
|------|----------------|--------|------------------|
| 生命周期是否阻塞页面 | CustomNode:OnAppear | 区间长度、计算子工作、线程状态 | 重计算移出 UI 生命周期后，预期该 UI 区间内的计算工作减少；在任务线程核对计算仍完成。事件名称本身不能唯一定位应用函数 |
| 首帧 ListItem 创建过多 | `Create[ListItem][self:节点ID]` | 首帧窗口中的创建调用及不同 self ID；包含首个 Vsync 前的页面构建 | ForEach 改为 LazyForEach 后，预期 ListItem 创建量减少；具体值含窗口内实际缓存/预创建项，详见 [列表验证](startup/list-creation.md#首帧-listitem-创建量的-trace-验证) |
| 懒加载项按需构建 | `Builder:BuildLazyItem` | 条目索引、缓存/预构建上下文，后缀随版本变化 | 辅助解释 LazyForEach 的创建时机；不能用此标签单独比较 ForEach 与 LazyForEach 的 ListItem 创建量 |
| 隐藏内容仍构建 | 目标面板初始化日志；首页的 `load page:` 与首帧 ReceiveVsync | 初始隐藏时是否仍初始化；页面加载和首帧处理耗时 | 改为首次条件创建后，预期未打开面板时不执行其初始化；两个区间分别比较，首次打开的工作单独观察 |
| 布局冗余 | Create[Column]、Measure[Column]、Layout[Column]、FlushLayoutTask | 目标子树节点 ID、创建和布局工作 | 删除无职责中间容器后，预期目标容器创建数及对应布局工作减少；耗时另测，不把整个应用的同名节点一并统计 |
| 同步图片可能影响布局 | FlushLayoutTask；文档案例 CreateImagePixelMap | 按资源和线程关联图片工作与布局等待 | 改异步后，预期 UI 首帧布局路径上的同步图片工作/等待减少；解码可能移到后台而非总次数减少，冷/热缓存分别比较 |
| 初始图片完成后尺寸变化 | 图片完成回调或业务打点、目标条目的 Measure/Layout | 首页首次展示至初始图片完成期间的尺寸变化和重复布局 | 已知比例提前占位后，由加载完成触发的布局应减少；首帧之后的工作不计入首帧耗时 |
| 首页整体等待非关键内容 | 区域就绪状态、目标子树创建与业务展示打点 | 关键内容首次显示、全部初始内容就绪，分别关联实际帧 | 分阶段展示后关键内容应更早可见；数据完成时间可能不变，不把骨架当完整内容 |
| 前置页进入首页时集中创建 | BuilderNode new/build、makeNode 与挂载计数或业务打点 | 准备时机、前置页首次显示及交互、进入首页到显示、存活数量 | 提前构建后进入阶段的创建工作减少；核对工作前移和内存代价，不将 build 完成当已送显 |
| 前述阶段不足以解释 | UITaskScheduler::FlushTask、FlushRenderTask | 阶段分布、剩余时间和线程状态 | 渲染集中：进一步人工定界；等待明显：检查对应调度数据；不直接归因某组件 |

每份指导至少回答：**为什么看它 → 看哪个区间/信息 → 看到不同结果分别查哪里**。不只列名字，也不把整张观察表无差别发给所有用户。

## 转场问题观察

按同一设备、版本、数据与动作比较，分别记录以下窗口。缓存与复用池的冷次、后续热切换独立统计，动画在用实例与空闲缓存分开。

| 窗口 | 起点与终点 | 要回答的问题 |
|---|---|---|
| 首次反馈 | 点击/切换动作 → 目标框架、骨架或首个目标内容实际显示 | 进入等待是否减少；明确此次终点是什么 |
| 动画过程 | 实际动画开始 → 结束 | 长帧、集中创建与布局是否改善，跟手与离手分开 |
| 内容就绪 | 目标动作 → 本次真实内容完整可用 | 工作是否只是后移，最终内容是否仍完整、可交互 |

| 疑点 | 观察对象与变化 | 结果分支与限制 |
|---|---|---|
| Swiper 邻页准备晚或过多 | 目标子树创建/布局、缓存窗口与存活节点，关联翻页动作 | 相关工作在进入前出现且命中时支持准备前移；仍落入进入窗口则检查生成方式与缓存范围。预加载内存另计，未写 cachedCount 不等于零缓存 |
| 图片等资源准备晚 | 按 ID/版本的请求、解码、命中和提交时刻，关联 onAnimationStart 与后续子页构建 | 请求已提前但未命中时查身份/时机/消费路径；资源已就绪仍慢则检查创建布局，不把整个动画长度归为资源等待 |
| 重负载子树集中 | 各批数据提交、目标节点 Create/Measure/Layout 与实际帧，见[共享分帧规则](component/frame-splitting.md) | 首批负载减少后也检查后续帧与最终就绪；一次 append 不等于一次独立送显，业务打点不包含全部后续测量 |
| 同父或跨页重复创建 | 复用规则中的创建/回收/命中计数，按父实例、类型和结构组识别 | 页内复用已有效但跨页持续新建时查池作用范围；共享池热切换仍无命中再查拥有者寿命与实际回收路径，不要求首批零创建 |
| 布局向外扩散 | 宿主尺寸、外部 Footer 等节点的位置及 Measure/Layout | 稳定业务允许的边界后外部工作应减少；目标内部必要布局保留，不能以同名事件总数代替目标节点 |
| 先骨架或提前 build | 已有[分阶段展示](startup/staged-display.md)和[提前构建](startup/home-prebuild.md)中的观察点 | 骨架出现与正文就绪分别计时；build 前移时扩大窗口核对前置页体验和内存，不把 build 完成当成上屏 |

帧预算按实际刷新率、工具帧数据和目标阶段判断，不把 400ms 动画时长当作单帧预算。必要函数体和业务路径已明确时可直接指出代码风险；采集用于验证收益或继续定界，不能作为所有建议的前置条件。

## 动效问题观察

| 疑点 | 参考名称/前缀 | 看什么 | 分支与限制 |
|---|---|---|---|
| 动画处理工作 | `RSThread::DoAnimation` | 实际事件的持续时间、子事件与所在帧 | 用于定位动画处理工作；结合当前刷新率、实际帧时间线与送显结果判断卡顿，不能仅由该事件的间隔或缺失证明掉帧 |
| Vsync 调度线索 | `FlushVsync` | 事件间隔、当前刷新率与帧关联 | 长间隙是进一步检查线索；按需渲染、帧率策略和事件采集条件也会改变间隔，不直接解释为 Vsync 阻塞或掉帧。需要时结合线程状态、App/RS Frame 及送显数据定位 |
| 渲染阶段集中 | `FlushLayoutTask`、`FlushRenderTask` | 总区间、节点名、重复现象 | 布局集中：回查布局属性动画或嵌套层级；渲染集中：查看绘制指令数量和重复绘制现象 |
| 动画属性更新频率与范围 | `ViewPU.viewPropertyHasChanged` | 关联组件、更新频率、范围 | 频率过高：核对是否有不可见组件仍在动效或冗余刷新；范围过大：回查状态绑定范围。事件受调试配置限制，不保证可见 |
| 不可见组件仍在刷新 | 同场景前后可比的录制 + 不可见区间的渲染事件 | 不可见区间内是否仍有状态更新与渲染工作 | 改为在 `aboutToDisappear`/`onPageHide`/`Tabs.onChange` 清理或接入可见性回调控停后，预期不可见区间内的属性更新与渲染工作减少；定时器与 `animator` 仍需显式停止 |

先确认问题窗口的实际刷新率与帧率策略：60Hz 的周期约 16.67ms，120Hz 约 8.33ms。周期用于理解当前帧预算，不是所有线程事件间隔的统一验收阈值；仅凭 `RSThread::DoAnimation` 或 `FlushVsync` 相邻事件间隔不能证明实际送显丢帧。工具有可靠帧时间线时，关联 App/RS Frame、帧截止时间与送显结果，再定位超时工作；区间持续时间与 CPU 执行时间分别看，缺少关联数据时说明只能定位工作阶段。参考[刷新率与帧周期](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-performance-3/)及[滑动帧分析](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-performance-53)。

上述观察点用于诊断已运行动画的掉帧、Vsync 间隙与渲染集中问题。各类动画优化的验证方法有不同适用口径，不在此复述；按建议类型查阅对应规则文件的「建议与验证」：

- animateTo 闭包缺失：用实际过渡/录屏核对视觉效果，状态起止日志只说明提交值；Trace可辅助分析工作量，但不能仅凭ReceiveVsync或RSThread事件证明插值——详见 [animateTo 规则](animation/animateTo-patterns.md#建议与验证)。
- 自定义动画改为系统 API：可对比动画窗口内应用 UI 线程 `ReceiveVsync` 总 Duration——详见 [animateTo 规则](animation/animateTo-patterns.md#建议与验证)。
- 布局属性改图形变换：效果等价时，比较实际动画窗口内目标子树的布局与渲染工作；只有录制能可靠关联目标节点时才用 Measure/Layout 归因，不能仅用触发时的 animateTo 同步调用耗时代表逐帧收益。
- 合并相同参数 animateTo、`animateTo`+`onFinish` 改为 `transition`：需要比较触发时的同步工作时，包围整个原事件回调；不以帧间隔证明少一次调用的收益——详见[动效实现方式](animation/animation-impl.md#建议与验证)。
- renderGroup 缺失与误用：以代码层前提条件核对为主，辅以 Frame trace 观察 render_service CPU 占比——详见 [renderGroup 规则](animation/render-group.md#建议与验证)。
- 第三方动画库（APNG、Lottie 等）控停：对比不可见区间 `ReceiveVsync` 总 Duration——详见 [冗余刷新规则](animation/redundant-refresh.md#建议与验证)。

## 滑动问题观察

| 疑点 | 搜索名称/前缀 | 看什么 | 结果分支及下一步 |
|------|----------------|--------|------------------|
| 复用收益 | 当前复用机制适用的创建/复用日志；相同滑动路径的帧耗时 | 后续滚动时的重复创建与帧处理耗时 | 按机制选择可用日志，首次创建与后续滚动分开比较；Trace 按相同路径、数据和缓存条件比较帧耗时 |
| LazyForEach 按需构建 | `Builder:BuildLazyItem` | 条目索引、实际生成方式与构建窗口 | 先核对版本和采集配置；缺失也可能是未进入该路径或使用 Repeat，不能直接判懒加载失效。持续构建时结合首次访问、缓存命中和滑动速度定位 |
| 懒加载预测 | `OnIdle`、`expiringItem_`、`List predict` | 实际版本中的预测任务与缓存范围 | 结合容器支持、空闲预算、可见范围和缓存配置解释；事件缺失或单个 count 不能直接证明 cachedCount 错误 |
| 布局是否承担主要工作 | `FlushLayoutTask` | 总区间、节点名 | 集中某节点：回查约束/容器/嵌套层级；不集中：转看回调或渲染 |
| 布局层级深 | `Layout[`、`Measure[` | 目标子树的节点 ID、测量/布局次数与容器职责 | 区分节点数与事件次数、可见内容与必要缓存；仅对无独立职责的容器评估精简，不按固定层数判缺陷 |
| Flex 重复测量 | `Measure` | 目标节点在同一帧的测量次数与约束 | 结合直接父容器及grow/shrink分配回查；不从任意后代属性推断外层重复测量，也不把2次变1次设为固定门槛 |
| 列表项布局计算 | `ListLayoutAlgorithm::MeasureListItem` | 滑动时每帧频率 | 大量出现：回查布局层级和条目复杂度 |
| JS 回调耗时 | `ExecuteJS` | 滑动时单次耗时和频率 | 频繁：回查高频回调内 hilog/耗时操作；耗时长：回查回调内重计算。注意：ExecuteJS 总量在 ForEach→LazyForEach 改造后可能因框架新增 totalCount 调用而反升，不应作为该改造的验证指标；scroll 场景下应以 `ReceiveVsync` 完整区间 Duration 验证帧处理耗时 |
| 渲染范围 | `FlushRenderTask` | 实际版本可用的参数、子事件与关联子树 | 关联当前动作和目标节点后评估无关更新；不能把所有事件参数都解释为跨版本通用的节点计数 |
| 组件创建与复用 | `Create[`、业务创建/复用计数 | 初次进入可视区、回收后再进入及实际命中路径 | 首次创建属于必要工作；已有回收/再加入机会仍重复构建时，再按当前 V1/V2 机制核对复用，不仅凭创建事件要求增加 @Reusable |

滑动预算按当前刷新率、完整帧工作和业务目标确定；Measure 次数、JS 调用次数与布局层数没有适用于所有页面的固定合格阈值。比较相同数据、路径、缓存和采集条件下的实际变化，区分首次构建、后续复用、局部工作与整帧耗时。缺事件先核对版本、采集标签、开关、进程和录制窗口，不能解释为零开销。

## 修改效果的观察方法

每项建议先说明整体收益，再分列适用的日志、Trace 等验证方法；两种都能验证时都写出，供开发者选择。各规则文件的“打点与预期变化”提供观察依据，整体耗时、局部次数、单次计算和线程迁移分别表达。Trace 需要新增业务打点时给出成对接口和实际插入代码，具体机制事件按需补充。开发者输出保留适用打点、条件及官方文档链接，无需附框架内部源码链接。

`APP:` 前缀在规则中表示建议由开发者新增的业务打点，不是框架已有标签，也不表示 bench 已经包含该业务打点。验证时两组使用相同插桩；业务点只覆盖声明的函数或处理区间，不能用父级大区间代替传参、序列化等具体成本。可参考 [HiTraceMeter 性能打点](https://gitcode.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-performance-analysis-kit/js-apis-hitracemeter.md)与 [常用 Trace 使用指导](https://gitcode.com/openharmony/docs/blob/master/zh-cn/application-dev/performance/common-trace-using-instructions.md)。

## 事件可见性

事件名称和可见性依系统版本、采集标签及调试开关而变化。`Create[ListItem]` 以及节点 Measure/Layout 事件受布局跟踪开关影响；当前框架实现需确认开发者模式与 `persist.ace.trace.layout.enabled`，缺事件时先检查采集条件，不能直接判断没有创建或开销。CreateImagePixelMap 是图片分析的参考名称，以实际录制为准。

## 异常与口径

- 找不到进程：确认包名、实际启动进程、录制时机和过滤条件。
- 找不到事件：核对工具/系统版本、采集标签、门控及时间窗；不是“零耗时”。
- 问题前半段缺失：核对是否过晚开始或缓冲区覆盖，调整后重采。
- 区间很长：墙钟持续时间不必然等于 CPU 执行时间，结合线程状态判断。没有调度数据就声明无法区分。
- 阶段结束：不等于首帧上屏；没有跨阶段关联就只报告可见范围。
- 工具版本未知：先问最小环境信息，提供通用操作目标和官方入口，不编造版本特定菜单。

## 首帧案例中的跨进程关联方法

[减少首帧绘制时的冗余操作](https://gitcode.com/openharmony/docs/blob/master/zh-cn/application-dev/performance/reduce-redundant-operations-when-render-first-frame.md)的“条件渲染”案例还给出以下人工观察方法：在 App 泳道找到页面加载后的第一个 ReceiveVsync，读取其中 H:MarshRSTransactionData 携带的 transactionFlag；在 render_service 泳道查找相同 transactionFlag 的 H:RSMainThread::ProcessCommandUni，再观察其所属 ReceiveVsync 区间。

该方法用于关联文档案例中的 render_service 首帧处理区间，不能将该区间长度直接等同于整个应用冷启动耗时，也不能仅凭它证明物理屏幕已送显。事件名、参数和链路依赖版本；缺少 transactionFlag 或关联事件时应说明无法建立此关联，核对版本与采集项，不能凭时间接近硬配对。本 Skill 只指导开发者观察，不解析 Trace。
