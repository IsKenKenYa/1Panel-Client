# 高性能深浅色切换

## 接入步骤

1. 确认有效产品、模块和平台版本，读取现有开关及颜色模式设置。
2. 按[兼容性规则](compatibility.md)检查属性更新，先完成需要的适配。
3. 在目标 `module.json5` 的 `module.metadata` 中合并以下项：

```json5
{
  "module": {
    "metadata": [
      {
        "name": "configColorModeChangePerformanceInArkUI",
        "value": "true"
      }
    ]
  }
}
```

上面仅展示配置位置。保留原有 module 内容和 metadata，不重复添加，不写布尔值 `true`。已有正确配置时检查兼容性并验证功能。

该能力从 API 20 起提供。区分编译 SDK、目标版本、最低兼容版本和设备版本：最低兼容版本较低不代表必须整体升级；需判断当前接入是否可编译、低版本是否可正常回退。Native 符号还需核对链接与加载条件。

## 更新机制

高性能开关改变了切换深浅色时的属性更新方式，这也是启用前需要检查兼容性的原因。

- **默认流程**：切换深浅色时，全量重新执行前端组件的属性设置。
- **高性能流程**：在仅颜色模式变化且满足优化条件时，主要更新已有组件中需要变化的颜色，减少全量执行前端代码。

性能改善来自减少切换时的前端函数执行和重复属性设置，降低 CPU 工作量，从而帮助缩短切换耗时、减轻卡顿。需要变化的颜色仍会更新和绘制。实际收益取决于页面与设备，应通过同场景对照判断。

统一资源引用可以正常换色，例如：

```ts
Text('标题').fontColor($r('app.color.title_color'))
```

为同一个 `title_color` 在 base 中定义黑色、dark 中定义白色。高性能流程保留这个资源引用，切换时重新读取对应颜色，即可完成更新。

需要检查的是“切换时重新选择资源”的业务逻辑。例如，业务代码在浅色时选择 `light_title`，深色时选择另一个资源 `dark_title`。高性能流程保留的是最初选中的资源引用，不能依赖切换时再次执行这段选择逻辑，自动改选另一个资源。

## 出现兼容性问题时的两个方案

例如原来用三元表达式按模式返回 `title_light` 或 `title_dark`，开启高性能后缺少重新选择资源的更新路径。应同时给开发者以下选择：

| 方案 | 怎么改 | 功能与性能取舍 |
| --- | --- | --- |
| 方案一：兼容更新 | 保留两个资源名和选择逻辑；V1 由 AppStorage、StorageLink/Watch 更新绑定状态，V2 按现有可观测状态更新 | 可恢复原有换色和业务联动；受影响属性仍执行前端更新，不能获得纯资源换色所减少的这部分开销 |
| 方案二：高性能资源 | 移除按模式选择两个资源的三元表达式等逻辑；使用同一个 title_color，在 base/dark 中分别配色，属性直接绑定 | 由资源更新流程读取对应颜色，无需为这项配色通过业务监听重新选择资源 |

纯配色优先推荐方案二；确需保留业务选择时使用方案一。交付时两个方案都需给出涉及文件的相对路径与完整代码，兼容方案覆盖首次显示初始化和后续变化；已正确的事件写入代码可明确复用。性能限制应限定到依赖前端更新的部分，不能说 StorageLink/Watch 会关闭整个组件或应用的高性能开关。完整代码见[兼容性规则与两种修复方案](compatibility.md)。

## 验证

冷启动即深色、浅→深、深→浅均要检查。验证资源、文本和业务联动；涉及反色时加入算法开/关对照。修改性能开关后重新构建、安装并重启进程，回退也采用这一方式。

### 用 trace 对比切换开销

需要对比默认与高性能的切换开销时，优先推荐通过 DevEco Studio Profiler 采集和分析 trace，两种模式各采集一次深浅色切换。无法使用 Profiler 或需要脚本化采集时，使用下方命令行备选方式。

1. 采集前确认：相同设备、相同页面、相同切换操作；修改开关后已重新构建、安装并重启进程。采集前打开目标页面，两组采用相同的切换及返回目标应用的操作顺序。
2. 性能对比只推荐通过系统设置（设置 > 显示和亮度 > 深色模式）触发切换。
3. 在 DevEco Studio Profiler 中采集目标应用的 trace：开始采集后通过系统设置执行一次深浅色切换，回到目标应用等待界面完成换色，再停止并保存记录。默认模式和高性能模式分别保存，便于对照。
4. 用 DevEco Studio Profiler 或其他 trace 查看工具打开文件，按目标应用进程过滤，定位应用主线程中 `OHOS::AppExecFwk::OHOSApplication::OnConfigurationUpdated` 之后的深浅色切换处理片段，按以下方法找到两种模式下要比较的 `Animate`：

   | 模式 | 目标 Animate 的定位方法 | 前端刷新特征 |
   | --- | --- | --- |
   | 开启高性能 | `AceContainer::UpdateColorMode` 下的 `Animate` | 通过颜色资源及属性更新完成换色，减少全量前端刷新 |
   | 未开启高性能 | 找到其下包含 `ViewFunctions::ExecuteReload` 的 `Animate` | 执行前端刷新，重新执行组件属性设置 |

5. 分别读取上述两个目标 `Animate` 从开始到结束的总耗时，对比未开启与开启高性能时的切换开销。`ViewFunctions::ExecuteReload` 用于识别未开启时的 `Animate` 及其前端刷新过程，不以该子调用的单独耗时作为本次总耗时。
6. 结合 `Animate` 内的前端刷新调用分析耗时差异：高性能减少的是前端刷新的次数，不会减少 measure 和 render 的次数，不以测量、布局或渲染打点次数减少作为生效判据。业务状态变化仍可能触发必要的前端更新。同时通过界面核对颜色和业务联动。

开启高性能通常可缩短深浅色切换的 Animate 总耗时，实际收益随页面组件规模与设备而定，以目标工程的实测为准；不以该定性预期替代实测，不将其作为收益承诺或验收依据。

#### 命令行采集（备选）

无法使用 DevEco Studio Profiler 或需要脚本化采集时，可使用 hitrace。`ace`、`ark`、`sched` 标签在 API 26 真机与模拟机上均已核实，`hdc shell "hitrace -l"` 可查看全部标签。采集前的环境确认、切换操作和分析方法与上述流程一致。

```bash
hdc shell "hitrace --trace_begin ace ark sched"
# 通过系统设置切换深浅色，回到目标应用等待界面完成换色
hdc shell "hitrace --trace_finish -o /data/local/tmp/color_switch.ftrace"
hdc file recv /data/local/tmp/color_switch.ftrace .
```

版本条件与官方来源见 [API 与适配依据](api-facts.md)。报告实际观测和覆盖范围；没有耗时/FPS 数据时不报告收益百分比。
