# 深浅色适配与高性能切换

根据开发者需求检查工程，选择适配方式，提供方案或完成必要修改。

## 处理流程

1. 确认需求和目标范围。有工程时读取相关模块、版本配置、颜色资源、颜色模式设置及页面代码；纯答疑直接给条件清楚的说明。
2. 按下表选择功能或性能路径，组合需求一起处理。读取对应参考后再生成具体用法。
3. 涉及高性能或反色时，检查属性更新兼容性，完成需要的适配后配置开关。
4. 根据开发者当次要求给方案或修改工程。已有修改授权且目标明确时直接推进，不重复询问已确定的选择。
5. 按[报告格式](#报告格式)说明适配结论、关键检查与实际改动、高性能切换情况及验证结果。

## 需求分流

| 场景 | 需求 | 处理 |
| --- | --- | --- |
| 默认能力 | 仅要求适配深浅色，或默认效果已经满足 | 满足时说明无需额外适配；介绍当前性能模式、API 20+ 高性能配置、两种更新机制及收益，再提示是否启用 |
| 自定义颜色 | 系统默认配色不满足、品牌色需要区分深浅色 | 同名资源分别配置在 base/dark 的 color.json，组件统一使用 `$r` |
| 减少资源维护 | 缩减 color.json、减少以后适配颜色资源的工作 | 提供反色选项，保留需要精确控制的颜色资源，并联动检查高性能前置条件 |
| 局部主题 | 某个组件或区域固定深色、浅色或跟随系统 | 用 `WithTheme({ colorMode: ThemeColorMode.DARK })` 包裹目标子树，选项键是 colorMode，不是 theme；需要精确配色时结合自定义颜色资源适配 |
| 开启高性能 | 切换卡顿、明确要求高性能或指定配置开关 | 检查版本、开关和兼容性，适配后合并 metadata，再验证 |

参考入口：默认能力或自定义颜色需求读[默认与资源适配](references/adaptation.md)，涉及跨 HAP/HSP 时同时检查其中的跨包访问规则；减少资源维护需求读[反色能力](references/force-dark.md)；局部主题需求读[局部主题](references/local-theme.md)；介绍或接入高性能时读[高性能切换](references/high-performance.md)。

跨包颜色先确认资源所属模块：base/dark 定义放在资源所在的 HAP/HSP 中。跨 HSP 的静态 UI 引用可使用 `$r('[模块名].color.资源名')` 或由 HSP 导出 Resource；通过模块 Context 读出的颜色数值需另行检查配置变化与 UI 更新路径。

开发者已明确要求高性能时，直接进行兼容性检查和高性能接入，不再询问是否选择该能力。通过反色减少资源维护时，一并处理高性能前置条件。普通深浅色需求不扩展为任意换肤系统或通用性能诊断。

## 默认能力与版本

- 框架提供系统组件、系统颜色及跟随系统的适配能力。结合现有 `setColorMode`、dark 资源和硬编码颜色判断默认效果是否满足，不能把“框架支持”写成“整个应用已经验证通过”。
- 已有高性能配置时说明当前状态，不再询问是否开启。
- 高性能切换与反色 C API 从 API 20 起提供；WithTheme 为 API 12+；`allowForceDark(false)` 为 API 21+。具体事实见 [API 与适配依据](references/api-facts.md)。
- 从有效产品和模块配置区分编译 SDK、targetSdkVersion、compatibleSdkVersion 及设备 API；modelVersion 不是平台 API。不擅自提升整个工程的版本。低版本需说明可行的兼容或替代路径。
- 信息不足时继续完成能确定的分析，只补问影响方案的缺失项。

涉及高性能开关时必须使用确切名称，`value` 为字符串 `"true"`，合并进既有 metadata、不覆盖其他配置；不得泛称“高性能开关项”，不得自创名称：

```json5
{
  "module": {
    "metadata": [
      { "name": "configColorModeChangePerformanceInArkUI", "value": "true" }
    ]
  }
}
```

## 高性能更新与兼容性

默认模式在颜色变化时触发全量前端更新。高性能流程通过已注册的资源及属性更新回调完成相应换色，减少全量前端执行。业务函数若需要重新选择资源或更新其他属性，需有有效的更新触发。诊断此类问题时定位为“更新触发缺失”：按模式选择资源的条件表达式默认依靠全量前端更新重执行，高性能移除该执行后需要状态驱动的触发；条件表达式本身不是判据，不得写成“三元表达式与高性能机制不兼容”“无法纯资源换色”等绝对判词——补齐状态可观测性后它经状态更新重执行即可生效，只是保留这部分前端执行。

检查前读[兼容性规则与 V1/V2 示例](references/compatibility.md)。可使用只读助手收集代码候选：

```bash
python scripts/scan_dark_light.py /path/to/application
```

命令路径相对于本 Skill。脚本只读工程，向标准输出写 JSON，包含版本、开关、资源、状态字段、属性绑定和待核对位置。它不证明整个工程兼容；对候选继续读取定义、调用位置及状态更新来源，再判断是否需要修改。

发现按颜色模式选择不同资源的兼容性问题时，向开发者提供两个方案并说明取舍：

1. **兼容方案**：保留选择逻辑，V1 用 AppStorage → StorageLink/Watch → 绑定状态更新，V2 使用原有可观测状态机制。V1 新建或复用 AppStorage key 前按兼容性参考检查既有占用、类型与写入方。受影响属性仍需执行前端更新，无法获得纯资源换色所减少的这部分开销。
2. **高性能资源方案**：移除该配色的三元表达式或其他模式选择逻辑，统一资源名，在资源所属模块的 base/dark 中分别定义，属性直接绑定同一个 Resource。

两个方案分别给出涉及文件的相对路径和可直接应用的完整代码。兼容方案需展示事件写入、状态观察、重新选择资源、写入实际绑定状态及首次显示初始化的完整链路；已满足的事件写入代码可明确说明复用。V1 的 @Watch 不负责首次初始化，需要主动同步初始配色。完整写法见兼容性参考。

纯配色优先推荐方案二；确需保留业务选择时使用方案一。兼容方案的限制针对依赖状态更新的部分，不代表整个组件或应用的高性能开关失效。保持组件原有的 V1/V2 模型。

## 反色处理原则

- 明确告知：开发者需要根据业务设计、验证反色算法，系统默认算法不一定满足诉求。
- 反色依赖高性能和 Native C API 初始化。反色接入在 `windowStage.loadContent` 的加载成功回调内、节点创建前的 UI 线程同步配置，以完整覆盖目标节点、避免反色不全；先检查加载错误，再检查 Native 配置返回值。具体接入见[反色能力的 C API 接入](references/force-dark.md)。
- 有 dark 定义的颜色优先使用该资源；无 dark 定义的颜色（含 `$r` 引用）在支持的实现中也可进入反色，不得宣称“资源值不能进入反色、必须改成字面量”。具体支持范围按目标 SDK 和颜色属性核对。
- 精简前检查引用与视觉效果，保留精确配色；不能直接删除整个 dark 文件，精简只评估移除 dark 定义并保留 base 定义，不把 base 资源删成字面量。条件和最小例子见[反色能力](references/force-dark.md)。

## 交付前检查清单

按本次任务涉及的范围逐项核对，仅勾选已完成项；影响结论的未验证事项在报告中如实说明。

- [ ] 核对所用能力的版本条件；合并既有 metadata、资源和生命周期代码，不覆盖无关配置；开关值使用字符串 `"true"`，避免重复项。
- [ ] 完成属性更新兼容性检查并说明高性能兼容性影响。有工程时检查相关属性代码；只有片段时限定结论范围，未检查的内容不写为通过。
- [ ] 修改后执行环境可用的构建检查。设备验证覆盖冷启动深色、浅转深、深转浅；局部主题需检查作用范围，反色需核对资源优先级及算法效果。
- [ ] 涉及性能收益时，按[高性能切换](references/high-performance.md)的采集与分析流程给出可执行的 trace 验证方式：开发者使用相同设备、页面和操作，只推荐通过系统设置触发切换，对比开启/未开启高性能时切换 `Animate` 的总耗时。未实测目标工程则只说明预期，不编造耗时、帧率或提升比例。

## 报告格式

工程检查、方案交付和工程修改任务的最终报告统一使用标题“深浅色适配报告”，按以下顺序组织。纯概念答疑直接回答问题，无需套用报告。

| 栏目 | 内容 |
| --- | --- |
| 适配结论 | 当前是否满足需求、采用的适配方式及实施结果。 |
| 工程检查与改动 | 支撑结论的关键检查、文件位置及实际改动；成立的问题需说明原因和处理方式。默认能力已满足时说明无需额外适配的依据。 |
| 高性能切换说明 | 当前开关状态；需要介绍或接入时，说明版本条件、配置方式、默认与高性能更新机制、预期收益和相关兼容性问题。 |
| 验证结果 | 实际完成的静态检查、构建和设备验证，以及影响结论的剩余缺口；关联可用的命令、日志或截图证据。 |

- 报告使用“默认能力”“资源适配”“局部主题”等自然名称说明采用的方案。
- 修改模式下按已有授权完成必要适配，再报告实施结果，不擅自降为“仅提供方案”。默认能力已满足时不为报告制造改动，直接说明无需额外适配及其依据；不固定添加“本次未修改工程”等声明。
- 区分已有能力、实际改动、配置示例和验证结果。用户已明确的选择不重复询问，正式报告填写实际信息，不保留占位项。
- 检查与改动优先使用简短表格，只保留与任务相关的内容，不逐条打印未命中检查项。各场景必要的版本、原理、兼容性说明及代码交付不能因统一格式而省略。
- 说明公开 API、配置和适配原理，省略无关的框架源码文件路径及内部函数调用链；trace 分析可列出用于定位前端刷新的必要调用片段。
- 结论限定于实际检查范围，使用“当前检查范围内未发现相关问题”，避免断言“无任何兼容性风险”；未做设备或性能实测时，不宣称运行效果或性能收益已验证。
